# Protocol contract

## Implementation status

The Chrome-to-native version-1 envelope is implemented and tested against JSON
golden vectors generated by the extension. The current native-host executable
keeps one bounded stream alive, validates each complete envelope, writes the
stable provider error `4900` (`Private wallet broker is unavailable.`) for each
valid request, and consumes valid cancellations without a response. Clean EOF
or the first terminal framing/state error closes the process with code 78. It
never opens public IPC because the executable constructs only a disabled
release attestation and release-disabled endpoint/executor.

The selected persistent runtime provides Windows binary stdio setup, a
4,096-frame session-wide ceiling, clean-EOF looping, strict combined inbound
sequencing, independent response sequencing, terminal malformed-input handling,
and cancellation without a response. The same dispatcher contains the future
attested composition seam: an injected downstream executor receives only an
owned `AuthorizedDispatch`; the host derives all correlation fields from that
sealed admission and does not allocate or flush the success/error response
until the executor returns completion. The default executable cannot reach that
seam, does not add broker IPC, and does not enable release attestation.

### Debug-only subprocess contract

An explicit `broker-ipc-contract-test-hook` Cargo feature can connect the native
host to a real Broker subprocess only when `debug_assertions` is also enabled.
The Broker has a separate `ipc-contract-test-hook` with the same double gate.
Ordinary builds, release builds with no features, and release builds with every
feature enabled all compile the disabled entrypoints: the Broker exits 78
immediately, while the native host emits only stable 4900 responses and exits 78
at EOF or the first terminal error. The hook is not release attestation and
cannot be selected by a release binary.

The debug native host derives the regular-file `broker` sibling in the same
build directory as its own executable; no environment variable or caller path
can select another program. It launches that child with hidden stdio, an empty
inherited environment, and unwind-safe kill/wait cleanup, and performs no
browser, GUI, wallet RPC, signing, Key Agent, or secret operation. The Broker's
local execution API is crate-private and absent unless tests or the debug hook
compile it. The internal stream uses a fixed 8,192-byte big-endian length
prefix and exact JSON structs. A version-1 hello
binds literal native-host/Broker roles, a nonzero client nonce, a nonzero server
nonce, and internal sequence 1. Every later command and response must preserve
both nonces and advance its own internal sequence by exactly one; malformed,
duplicate, skipped, cross-role, cross-nonce, or cross-session input terminates
the connection without resynchronization. The hello is outside Broker's
independent lifetime count: exactly 4,096 post-handshake commands may be
dispatched, and the next complete frame fails before Broker state mutation or a
response.

Only three post-handshake command forms exist:

- `eth_chainId` carries the already strict version-1 request with an empty
  parameter array and the permission route. Broker owns admission, the Sepolia
  chain-ID result, and completion before acknowledging it.
- `unavailable` carries only the nonzero session ID, extension request sequence,
  activation nonce, request ID, a fresh request nonce, and one closed enum for an
  allowlisted non-chain-ID method. It cannot carry raw JSON parameters, message
  bytes, accounts, addresses, origins, or an arbitrary method string. Broker
  consumes the shared extension sequence, records the correlation as completed,
  and returns an exact acknowledgement before the native host emits stable 4900.
- `cancel` carries the exact original request sequence and correlation plus a
  fresh cancellation nonce. In this synchronous secretless hook, the request is
  already complete; Broker must return `already-completed`. The acknowledgement
  stays internal and Chrome receives no cancellation response.

The three sequence domains are intentionally distinct: extension requests and
cancellations share one exact sequence, native responses use a separate exact
response-only sequence, and Broker IPC commands/responses use their own exact
handshake-relative sequences. This prevents a locally unavailable request or a
response-free cancellation from creating a gap before a later chain-ID request.
On reconnect the extension samples a new session ID, resets connection-local
sequences to one, and rejects any response from the old session. A real headless
test covers chain ID, parameter-free unavailable completion, late cancellation,
continued use of the same two subprocesses, old-process exit 78, session
rotation, and a successful chain-ID request on the new subprocess pair.

This is contract-path evidence only. The nonces prevent accidental stream
mix-up; they do not authenticate a process running as the same user. A sibling
path is still not an authenticated or attested bootstrap. Windows
endpoint SID/DACL policy, remote-client rejection, held executable identity,
signed installation evidence, and the release-attested downstream composition
remain stop-ship.

The approval-channel library establishes the private inherited Windows pipes,
restricted launch, exact request/response framing, monotonic deadlines,
held-child identity, and one-shot transcript. The parent-side Secret Input API
now owns an equivalent atomic launch: separate private request/response pipes,
an explicit child stdin/stdout/stderr handle list, canonical prompt transfer and
request EOF, a concrete bounded response reader, and the held process/job. It
binds the exact prompt and manifest-derived role to file/process/LPAC identity
and a fresh OS-CSPRNG challenge. Every read is deadline-cancellable and drained;
the parent reads through EOF with a `MAX_RESPONSE_BYTES + 1` overflow sentinel.
Accepted bytes remain zeroizing, cancellation remains separate, and the
non-clone proof can be consumed only for the same prompt. Approval and
secret-input default executables remain disabled with exit 78, and the missing
compiled release policy prevents restricted launch. Direct-launch parent
identity denial and signed-artifact end-to-end tests remain stop-ship. Typed and
kernel-level tests are necessary evidence, not an end-to-end release claim.

## Public framing

The framing library accepts strict UTF-8 JSON only, caps each direction at
1,048,576 bytes, and checks the exact four-byte native-endian length before
allocation. It rejects duplicate object keys, trailing roots, excessive nesting,
aggregate nodes/container items, and non-object roots.

Version 1 is fixed rather than negotiated. The host rejects unknown keys,
versions, roles, kinds, routes, and method names. It accepts only fixed-width
lowercase hexadecimal identifiers and JavaScript-safe integers. A 32-byte
session nonce prevents accidental mix-up; it does not authenticate another
process running as the same Windows user.

### Extension request

An extension request has exactly these top-level keys:

`namespace`, `version`, `role`, `kind`, `sessionId`, `sequence`,
`deadlineUnixMs`, `profileInstallId`, `activationNonce`, `requestId`, `method`,
`params`, `route`, and `context`.

- Literal values are `your-wallet`, `1`, `extension`, and `request`.
- `sessionId`, `profileInstallId`, and `activationNonce` are nonzero 32-byte
  lowercase hex. `requestId` is nonzero 16-byte lowercase hex.
- `sequence` and `deadlineUnixMs` are positive JavaScript-safe integers.
- `route` is exactly `permission`, `read`, or `signing` and must equal the route
  independently recomputed from the method firewall.
- `params` must pass the method-specific broker schema and aggregate bounds.

`context` has exactly `browserFamily`, `extensionId`, `tabId`, `frameId`,
`documentId`, `topOrigin`, `frameOrigin`, `documentLifecycle`, and
`channelNonce`. Version 1 requires `chrome`, a 32-character lowercase `a`-`p`
extension ID, a JavaScript-safe tab ID, frame zero, the bounded Chrome document
ID grammar, identical canonical HTTPS origins, `active`, and a nonzero 32-byte
channel nonce.

### Cancellation

A cancellation has exactly `namespace`, `version`, `role`, `kind`, `sessionId`,
`sequence`, `activationNonce`, `requestId`, `requestSequence`, and `reason`.
`kind` is `cancel`; the original request sequence must be positive and lower
than the cancellation sequence. The ASCII reason grammar is bounded to 128
bytes. The broker cancels only when session, activation, request ID, and original
request sequence all match.

### Native response

A response has exactly `namespace`, `version`, `role`, `kind`, `sessionId`,
`sequence`, `requestSequence`, `activationNonce`, `requestId`, and exactly one of
`result` or `error`. The native role is `native-host`. Native output has its own
strictly increasing sequence. The currently reachable executable emits only the
typed, stable unavailable error and no signing result. The persistent
dispatcher contains a dormant attested branch that can encode a downstream JSON
`result` or a bounded integer-code/string `error` with optional `data`, while
keeping every correlation field host-owned; the default executable cannot
enter that branch.

## Browser context

The extension accepts only an active, non-incognito, top-level HTTPS document
and binds the request to browser family, local profile-install ID, extension ID,
tab ID, frame ID, document ID, per-activation nonce, top/frame origin, port
lifetime, and the explicit provenance label `BrowserReportedUnverified`.
Browser URL paths, queries, fragments, incognito state, and page-supplied context
do not cross the extension boundary.

Navigation, page hide/freeze, detachment, origin change, service-worker restart,
extension update, broker/key-agent restart, lock, suspend, chain change, timeout,
or cancellation terminally invalidates a pending approval.

The MV3 manifest declares `incognito: "not_allowed"`, retains only the
`nativeMessaging` and `storage` permissions, and has no `host_permissions`.

The page-world provider also implements EIP-6963 discovery. Each top-level HTTPS
document receives one cryptographically sampled UUIDv4 and one immutable
provider identity. The provider, its metadata, and the announced detail object
are frozen; the embedded 96-by-96 icon is a local PNG data URI rather than SVG
or a remote resource. The wallet announces once at installation and reannounces
the exact same detail object for each later `eip6963:requestProvider` event.
It never overwrites an existing `window.ethereum` provider. These discovery
claims do not make the currently disabled native runtime release-eligible.

## Broker forwarding gate

Parsing a request does not authorize forwarding. The broker recomputes the
method route, validates the method-specific parameter schema, consumes the one
request/cancellation wire sequence, and binds pending state to the exact
session, document, activation, origin, and request ID.

Read-RPC and signing targets additionally require an existing permission for
the exact active account, active chain, profile installation, extension, and
origin. Signing methods must name that active account in their method-specific
account field. Permission-route operations remain local and cannot be mislabeled
as RPC or signing work.

## Private typed channel

The target broker/key-agent/helper channel uses a deterministic bounded binary
codec. External data is represented by `Untrusted*` types. Only validated
constructors can produce `CanonicalOperation`, the label-free
`approval_wire::ApprovalDisplay`, or `ApprovalBinding`. `approval-wire` alone
defines the `YWAPPR02`/`YWAPRS02` framing and validates stable semantic tags,
security-critical bits, required/forbidden operation shapes, duplicates,
bounds, risk, and expiry. The Key Agent encoder and native frontend use that
same crate. Labels and fixed ordering are owned only by `approval-ui`; no caller
label crosses the channel. The key agent never parses JSON, ABI descriptions,
HTML, or arbitrary prompt text.

The crate-private Key Agent offline-lifecycle channel is a separate closed
protocol (`YWOFREQ1`/`YWOFRES1`, version 1). Every request binds a nonzero
request ID, exact sequence, absolute local deadline, declared payload length,
and zero reserved fields, and is read through EOF under a 64-byte cap. One
controller activation accepts at most 64 exact sequential one-shot request
channels and never forgets an identifier during that lifetime; duplicate,
older, skipped, expired, and exhausted requests receive distinct stable codes
and lock decrypted state. Admission converts the bounded wall-clock remainder
to a locally pinned monotonic `Instant`; every sealed helper receives the exact
absolute expiry, and the controller rechecks the monotonic deadline after the
helper returns. That check mints a non-clone capability whose private fields
and constructor exist only in the controller. Every service/session mutation
must consume that exact capability. The capability retains the controller's
trusted clock and rechecks the same pinned monotonic expiry again after
password KDF, derivation, randomness, sealing, or resealing, at the last safe
point immediately before a durable commit, unlock, or pending-state mutation.
An expired or failed final clock sample locks the service without advancing the
durable generation or activating decrypted state.
Only status, 12/24-word create, separate backup-display and confirmation stages,
open, lock, and confirmed-address lookup exist. The create/open/recovery frames
have no payload at all, so the Broker cannot submit a password, mnemonic, or
confirmation answer as proof. Those values must come from crate-sealed Secret
TCB frontend capabilities. Frontends can only acquire zeroizing password or
confirmation input, or present a borrowed recovery view; they never receive the
vault service. Recovery display first returns a non-clone, live-session-bound
`DisplayedRecovery` without changing session state. Only a successful deadline
recheck can consume it into one in-memory challenge, and the later confirmation
command consumes that exact challenge and a fresh opaque binding. Lock, error,
restart, cross-stage use, or replay clears or rejects the pending challenge.
The compiled capability is intentionally
unavailable until authenticated one-shot helper adapters and the inherited
Windows channel are implemented; the Key Agent executable therefore still
exits 78.

The display projection separately carries origin/provenance, account, network,
chain ID, genesis and rule-set identity, RPC observation digest, operation kind,
and simulation provenance. Transaction displays additionally carry envelope,
nonce, target, native value, gas limit, the exact applicable fee fields,
checked maximum total fee, full bounded calldata and hash, and the complete
canonical access list. Personal-sign displays carry every exact message byte.
No display value is truncated. EIP-712 authorization remains fail-closed until
the native frontend can render the exact structured document.

The wire reply contains only `decision`, the exact digest, and a one-time nonce.
The Key Agent first creates one crate-private opaque `PreparedApprovalPrompt`,
sampling expiry once and retaining the exact request and its domain-separated
hash. Creation requires a freshly loaded, confirmed protected-settings record.
The prompt carries a non-clone settings lease containing its authenticated
generation, phrase revision, canonical record digest, exclusive owner evidence,
process-instance nonce, and fresh one-time lease nonce. The Windows channel
binds the full request hash (including the local anti-phishing phrase, risk, and
every display field) and held helper identity into a fresh transcript. Immediately
before authorization and signing, the Key Agent consumes the lease once and
freshly reloads the same record; lock, phrase rotation, owner takeover, restart,
record equivocation, or replay rejects the prompt. Authorization then consumes
the same request hash and a non-clone `VerifiedApprovalResponse`. Rebuilding a
shorter-lived request after the UI hold, or substituting any
phrase/display/expiry byte, is rejected. Development
builds contain no compiled release policy and default helper builds exit 78, so
the otherwise implemented opt-in runtime entry point cannot be launched by the
restricted release path or reach signing. A challenge expires after at most 120
seconds and can be consumed once; the TCB clamps it to the browser request's
remaining deadline.

## Durable broadcast handoff

Transaction signing is coupled to the concrete encrypted Key Agent journal.
The public signed artifact contains only transaction hash and sender; it is
non-clone and contains no spendable wire bytes. `begin_broadcast` first commits
`Broadcasting`, then returns a non-clone lease whose consuming `submit` method
is the only raw-byte path. Exact local and endpoint hashes commit `Submitted`.
Timeout, transport/RPC error, mismatch, abandoned lease, or crash recovers as
`BroadcastUnknown`; an ambiguous storage commit forces reload and never
releases the nonce.

## Native-host manifest

`extension/native-host/com.your_wallet.native.json.template` is intentionally
not installable. Its extension ID and executable path are placeholders, and the
release validator rejects placeholders. A rendered manifest must contain the
exact host name, `stdio`, one absolute Windows executable path, and exactly one
`chrome-extension://<32 lowercase a-p characters>/` origin.

No installer or registry writer is included. The syntactic validator does not
attest install-path ACLs, Authenticode identity, artifact hashes, registry ACLs,
or private broker pipe security; all remain stop-ship release evidence.
