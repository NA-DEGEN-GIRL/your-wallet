# Protocol contract

## Implementation status

The Chrome-to-native version-1 envelope is implemented and tested against JSON
golden vectors generated by the extension. The current native-host executable
keeps one bounded stream alive, validates each complete envelope, writes the
stable provider error `4900` (`Private wallet broker is unavailable.`) for each
valid request, and consumes valid cancellations without a response. Clean EOF
or the first terminal framing/state error closes the process with code 78. It
never opens public IPC because the executable constructs only a disabled
release attestation and release-disabled endpoint/executor.

The selected persistent runtime provides Windows binary stdio setup, a
4,096-frame session-wide ceiling, clean-EOF looping, strict combined inbound
sequencing, independent response sequencing, terminal malformed-input handling,
and cancellation without a response. The same dispatcher contains the future
attested composition seam: an injected downstream executor receives only an
owned `AuthorizedDispatch`; the host derives all correlation fields from that
sealed admission and does not allocate or flush the success/error response
until the executor returns completion. The default executable cannot reach that
seam, does not add broker IPC, and does not enable release attestation.

Separately, the ordinary library's dormant Broker admission retains the opaque
whole-release `AttestedArtifactDigest` from one successful `ReleaseAttestation`
inside `PreflightBrokerArtifact` and carries it unchanged into
`PreparedReleaseBrokerSupervisor`. This is the overall `ReleasePolicy`
`ArtifactDigest`. The dedicated Broker/helper manifest digest and the same-held
file's `FILE_ID_INFO` remain separate policy and exact-object proofs. The opaque
release identity is not placed on the wire or exposed as raw bytes. Its
retention does not construct a Broker-plus-Key-Agent same-release aggregate,
topology or single-instance proof, or runtime/signing authority. No production caller
reaches the dormant Broker path.

### Debug-only subprocess contract

An explicit `broker-ipc-contract-test-hook` Cargo feature can connect the native
host to a real Broker subprocess only when `debug_assertions` is also enabled.
The Broker has a separate `ipc-contract-test-hook` with the same double gate.
Ordinary builds, release builds with no features, and release builds with every
feature enabled all compile the disabled entrypoints: the Broker exits 78
immediately, while the native host emits only stable 4900 responses and exits 78
at EOF or the first terminal error. The hook is not release attestation and
cannot be selected by a release binary.

The original debug native host derives the regular-file `broker` sibling in the
same build directory as its own executable; no environment variable or caller
path can select another program. It launches that child with hidden stdio, an
empty inherited environment, and unwind-safe kill/wait cleanup, and performs no
browser, GUI, wallet RPC, signing, Key Agent, or secret operation. The Broker's
local execution API is crate-private and absent unless tests or the debug hook
compile it. The stdio adapter owns a four-byte big-endian length prefix and an
8,192-byte JSON-payload ceiling. A version-1 hello
binds literal native-host/Broker roles, a nonzero client nonce, a nonzero server
nonce, and internal sequence 1. Every later command and response must preserve
both nonces and advance its own internal sequence by exactly one; malformed,
duplicate, skipped, cross-role, cross-nonce, or cross-session input terminates
the connection without resynchronization. The hello is outside Broker's
independent lifetime count: exactly 4,096 post-handshake commands may be
dispatched, and the next complete frame fails before Broker state mutation or a
response.

Only three post-handshake command forms exist:

- `eth_chainId` carries the already strict version-1 request with an empty
  parameter array and the permission route. Broker owns admission, the Sepolia
  chain-ID result, and completion before acknowledging it.
- `unavailable` carries only the nonzero session ID, extension request sequence,
  activation nonce, request ID, a fresh request nonce, and one closed enum for an
  allowlisted non-chain-ID method. It cannot carry raw JSON parameters, message
  bytes, accounts, addresses, origins, or an arbitrary method string. Broker
  consumes the shared extension sequence, records the correlation as completed,
  and returns an exact acknowledgement before the native host emits stable 4900.
- `cancel` carries the exact original request sequence and correlation plus a
  fresh cancellation nonce. In this synchronous secretless hook, the request is
  already complete; Broker must return `already-completed`. The acknowledgement
  stays internal and Chrome receives no cancellation response.

The three sequence domains are intentionally distinct: extension requests and
cancellations share one exact sequence, native responses use a separate exact
response-only sequence, and Broker IPC commands/responses use their own exact
handshake-relative sequences. This prevents a locally unavailable request or a
response-free cancellation from creating a gap before a later chain-ID request.
On reconnect the extension samples a new session ID, resets connection-local
sequences to one, and rejects any response from the old session. A real headless
test covers chain ID, parameter-free unavailable completion, late cancellation,
continued use of the same two subprocesses, old-process exit 78, session
rotation, and a successful chain-ID request on the new subprocess pair.

The separate Windows-only `windows-broker-channel-contract-test-hook` composes
the same closed typed state machine with the dormant authenticated channel. It
also requires debug assertions; enabling every feature in a release build still
selects the disabled 4900/exit-78 native host and exit-78 Broker. The Windows
channel is the only framing owner: it writes the same four-byte big-endian
prefix around one exact JSON payload of at most 8,192 bytes, while Broker IPC
consumes payloads only. The legacy stdio adapter remains its own single framing
owner, so neither composition can double-frame.

Before any Broker user-mode code runs, a fresh debugger thread compares the
simultaneously held `broker.exe` artifact with the first
`CREATE_PROCESS_DEBUG_EVENT.hFile` using the volume serial and all 128
`FILE_ID_INFO` bits. Zero, all-zero, and all-`FF` identities fail closed. Process
creation uses `HANDLE_LIST = [restricted parent process, shared read/write
NUL]`, with stdin, stdout, and stderr all set to that same NUL handle through
`STARTF_USESTDHANDLES`. Its separate `JOB_LIST = [job]` names the retained
one-process kill-on-close Job. It also uses a hidden window policy and a minimal
two-variable Unicode environment. The named pipe has one protected
current-logon DACL entry, rejects remote clients and a second server instance,
and binds both ends to retained process objects plus the pipe-reported process
and session identities. It never reopens a process from a PID. Partial frames,
deadline expiry, peer exit, replay, and the frame/4,096-command limits are
terminal. Hidden process tests cover exact 8,192-byte framing, mapped-image
mismatch before user mode, hung-child Job cleanup, and an actual
native-host-to-Broker chain-ID/unavailable exchange.

This remains contract-path evidence, not release attestation. Chrome launches
the native host, so this slice cannot independently prove that the running
native-host image is the expected signed file before it handles Chrome stdio.
An immutable signed install, protected native-messaging registration, a stable
release extension ID, and end-to-end signed artifact evidence are external
blockers. The debug-held Broker is not an Authenticode release allowlist. RPC,
accounts, signing, and Key Agent access remain unrepresentable and unavailable.

The approval-channel library establishes the private inherited Windows pipes,
restricted launch, exact request/response framing, monotonic deadlines,
held-child identity, and one-shot transcript. Its `HANDLE_LIST` names exactly
two synchronous server pipe objects inherited by the child: stdin and one
response-pipe handle-table entry assigned as numerically equal stdout and
stderr. The parent retains the corresponding overlapped client ends. It does
not place parent-proof handles in that list. While the Approval child is still
suspended, the launcher remotely injects parent-process and parent-image proof
handles with inheritance disabled.

The runtime-enabled Approval child makes inspection and sealing of those two
unique objects its first Windows/CRT application operation, before binary-mode
conversion or protocol/UI work. It requires stdin to differ from stdout,
requires numeric `stdout == stderr`, requires both objects to be exact `PIPE`s
with preflags exactly `HANDLE_FLAG_INHERIT`, attempts both inherit-bit clears
without rollback, and accepts only exact-zero readback for both. It then
verifies the Approval LPAC, Job, and pipe peer and requires the sealed stdin,
shared output pipe, process proof, and image proof to be four pairwise-distinct
exact objects with zero flags. Only fresh child-local duplicates become
authoritative and remain retained through response write; the launcher-known
original injected slots are never adopted and are left only for bounded
process-exit cleanup. The child derives the authoritative parent PID
and process-token `TokenSessionId` from the retained live exact parent process
handle. For the synchronous server ends held by the child (whose overlapped
client ends remain with the parent), it requires the parent-hello PID, both
`GetNamedPipeClientProcessId` and `GetNamedPipeClientSessionId` observations,
and the child token session to match that exact process-derived identity. It
retains and revalidates the binding across UI presentation and response write.
While the retained process handle is live, this prevents PID-reuse substitution
and corroborates the pipe observations against the exact live parent process
object. It does not prove exclusive endpoint ownership, endpoint
topology/exclusivity, or per-write attribution because pipe handles remain
transferable and duplicable. The image check applies
case-preserving exact normalized path-string equality: it normalizes only an
optional `\\?\` prefix and separators and compares the live process image path
with a separate held file's final path; a casing mismatch fails closed. It then
checks the held path's `\\key-agent.exe` suffix and version metadata, supplies
the held handle plus path to Authenticode signer validation, and computes SHA-256
through a cloned held handle against the compiled parent policy. It does not prove that the live process was mapped
from that exact file object.

The parent-auth exchange is fixed rather than negotiated. Its order is a
62-byte parent hello; a 106-byte child hello that echoes the fresh nonzero parent
nonce, adds a fresh nonzero child nonce, and carries the domain-separated
SHA-256 bootstrap-transcript hash; a 110-byte parent-finish header followed by
the exact request and request EOF; then one fixed 75-byte response and response
EOF. The parent-finish header binds both bootstrap nonces, the canonical
Approval request hash, and the exact request length. Substitution, truncation,
trailing bytes, bad lengths, or cross-frame decoding fail closed. After the
response and EOF, the parent locally hashes the held child PID and helper file
identity, manifest digest, profile revision, request digest, one-shot Approval
nonce and canonical request hash, exact response bytes, fresh local channel
challenge, and both bootstrap nonces. Job policy/membership is a live gate, not
hashed identity. The fixed 75-byte response is ordered as magic, version,
decision, request digest, and the one-shot Approval request nonce. Only the
digest and nonce echo request fields; neither bootstrap nonce is echoed. Replay
resistance therefore also depends on the private one-shot endpoint and a fresh
one-shot Approval request nonce.

A repo-local child/grandchild kernel test makes a separate positive sentinel
inheritable and uses `CompareObjectHandles` to prove that the sentinel, but
neither original stdio object, reaches a broad-inheritance grandchild. The
sequential clears are non-atomic and do not prevent later re-enabling or
explicit duplication. This remains a two-object negative, not a four-object
grandchild proof; it is neither exhaustive stray-handle enumeration nor
evidence for the exact signed artifact, intended topology, immutable
installation, DLL/dependency identity, or release activation. Signed
release-path positive evidence covering case-sensitive directories and
alternate path forms, live mapped exact-file-object proof, the complete
DLL/dependency graph, immutable installation, a supervisor-held activation
capability, and exact endpoint topology/exclusivity remain **STOP-SHIP**. There
is no positive kernel availability test proving that the zero-capability
Approval LPAC can complete `OpenProcessToken(parent)`, so the new handle-first
success path remains release-unproven. The repository also has zero production
orchestration callers composing `launch_approval_frontend`
through a verified response into signing and no positive signed-handshake E2E.
Raw or legacy direct Approval launch cannot complete the parent-auth exchange
and fails silently. Default Approval builds still exit 78, and
`COMPILED_PARENT_POLICY` and `COMPILED_RELEASE_POLICY` remain `None`.

The parent-side Secret Input API now owns an equivalent atomic launch: separate
private request/response pipes,
an explicit `HANDLE_LIST` containing only the child stdin and shared
stdout/stderr pipe objects, canonical prompt transfer and request EOF, a concrete
bounded response reader, and the held process/job. Once the child exists
suspended and its Job/LPAC token are verified, the launcher remotely duplicates
the parent-process and image-file proof handles into it with inheritance
disabled, before resume. It binds the exact prompt and manifest-derived role to
file/process/LPAC identity and a fresh OS-CSPRNG challenge. Every read is
deadline-cancellable and drained; the parent reads through EOF with a
`MAX_RESPONSE_BYTES + 1` overflow sentinel.

The runtime-enabled Secret Input/recovery child makes validation and sealing of
its two unique stdio pipe objects the first Windows/CRT application operation:
both must carry exact inherit-only flags before the two clears and exact-zero
flags afterward. Immediately after the fixed parent hello, it requires those
two objects plus the injected process/image proofs to be four pairwise-distinct
exact objects with zero flags. A positive-control repo-local grandchild test
uses `CompareObjectHandles` to show that none of those four exact objects
propagates. The sequential stdio clears are non-atomic and do not prevent later
re-enabling or explicit duplication; this is not exhaustive stray-handle
enumeration or signed-artifact/topology/immutable-install evidence.

Accepted bytes remain zeroizing, cancellation remains separate, and the
non-clone proof can be consumed only for the same prompt. Approval and
secret-input default executables remain disabled with exit 78, and the missing
compiled release policy plus `COMPILED_PARENT_POLICY = None` prevent release
activation. Raw or legacy Approval launch fails without diagnostics; direct-
launch parent-identity denial and signed-artifact end-to-end tests remain
stop-ship evidence. Typed and kernel-level tests are necessary evidence, not an
end-to-end release claim.

## Public framing

The framing library accepts strict UTF-8 JSON only, caps each direction at
1,048,576 bytes, and checks the exact four-byte native-endian length before
allocation. It rejects duplicate object keys, trailing roots, excessive nesting,
aggregate nodes/container items, and non-object roots.

Version 1 is fixed rather than negotiated. The host rejects unknown keys,
versions, roles, kinds, routes, and method names. It accepts only fixed-width
lowercase hexadecimal identifiers and JavaScript-safe integers. A 32-byte
session nonce prevents accidental mix-up; it does not authenticate another
process running as the same Windows user.

### Extension request

An extension request has exactly these top-level keys:

`namespace`, `version`, `role`, `kind`, `sessionId`, `sequence`,
`deadlineUnixMs`, `profileInstallId`, `activationNonce`, `requestId`, `method`,
`params`, `route`, and `context`.

- Literal values are `your-wallet`, `1`, `extension`, and `request`.
- `sessionId`, `profileInstallId`, and `activationNonce` are nonzero 32-byte
  lowercase hex. `requestId` is nonzero 16-byte lowercase hex.
- `sequence` and `deadlineUnixMs` are positive JavaScript-safe integers.
- `route` is exactly `permission`, `read`, or `signing` and must equal the route
  independently recomputed from the method firewall.
- `params` must pass the method-specific broker schema and aggregate bounds.

`context` has exactly `browserFamily`, `extensionId`, `tabId`, `frameId`,
`documentId`, `topOrigin`, `frameOrigin`, `documentLifecycle`, and
`channelNonce`. Version 1 requires `chrome`, a 32-character lowercase `a`-`p`
extension ID, a JavaScript-safe tab ID, frame zero, the bounded Chrome document
ID grammar, identical canonical HTTPS origins, `active`, and a nonzero 32-byte
channel nonce.

### Cancellation

A cancellation has exactly `namespace`, `version`, `role`, `kind`, `sessionId`,
`sequence`, `activationNonce`, `requestId`, `requestSequence`, and `reason`.
`kind` is `cancel`; the original request sequence must be positive and lower
than the cancellation sequence. The ASCII reason grammar is bounded to 128
bytes. The broker cancels only when session, activation, request ID, and original
request sequence all match.

### Native response

A response has exactly `namespace`, `version`, `role`, `kind`, `sessionId`,
`sequence`, `requestSequence`, `activationNonce`, `requestId`, and exactly one of
`result` or `error`. The native role is `native-host`. Native output has its own
strictly increasing sequence. The currently reachable executable emits only the
typed, stable unavailable error and no signing result. The persistent
dispatcher contains a dormant attested branch that can encode a downstream JSON
`result` or a bounded integer-code/string `error` with optional `data`, while
keeping every correlation field host-owned; the default executable cannot
enter that branch.

## Browser context

The extension accepts only an active, non-incognito, top-level HTTPS document
and binds the request to browser family, local profile-install ID, extension ID,
tab ID, frame ID, document ID, per-activation nonce, top/frame origin, port
lifetime, and the explicit provenance label `BrowserReportedUnverified`.
Browser URL paths, queries, fragments, incognito state, and page-supplied context
do not cross the extension boundary.

Navigation, page hide/freeze, detachment, origin change, service-worker restart,
extension update, broker/key-agent restart, lock, suspend, chain change, timeout,
or cancellation terminally invalidates a pending approval.

The MV3 manifest declares `incognito: "not_allowed"`, retains only the
`nativeMessaging` and `storage` permissions, and has no `host_permissions`.

The page-world provider also implements EIP-6963 discovery. Each top-level HTTPS
document receives one cryptographically sampled UUIDv4 and one immutable
provider identity. The provider, its metadata, and the announced detail object
are frozen; the embedded 96-by-96 icon is a local PNG data URI rather than SVG
or a remote resource. The wallet announces once at installation and reannounces
the exact same detail object for each later `eip6963:requestProvider` event.
It never overwrites an existing `window.ethereum` provider. These discovery
claims do not make the currently disabled native runtime release-eligible.

## Broker forwarding gate

Parsing a request does not authorize forwarding. The broker recomputes the
method route, validates the method-specific parameter schema, consumes the one
request/cancellation wire sequence, and binds pending state to the exact
session, document, activation, origin, and request ID.

Read-RPC and signing targets additionally require an existing permission for
the exact active account, active chain, profile installation, extension, and
origin. Signing methods must name that active account in their method-specific
account field. Permission-route operations remain local and cannot be mislabeled
as RPC or signing work.

## Private typed channel

The target broker/key-agent/helper channel uses a deterministic bounded binary
codec. External data is represented by `Untrusted*` types. Only validated
constructors can produce `CanonicalOperation`, the label-free
`approval_wire::ApprovalDisplay`, or `ApprovalBinding`. `approval-wire` alone
defines the `YWAPPR02`/`YWAPRS02` framing and validates stable semantic tags,
security-critical bits, required/forbidden operation shapes, duplicates,
bounds, risk, and expiry. The Key Agent encoder and native frontend use that
same crate. Labels and fixed ordering are owned only by `approval-ui`; no caller
label crosses the channel. The key agent never parses JSON, ABI descriptions,
HTML, or arbitrary prompt text.

### Key Agent storage-startup handshake

The private Windows storage-startup protocol is a fixed one-shot exchange, not a
general Key Agent command channel. Its 188-byte `YWKSREQ1` version-1 request has
an exact declared length and zero reserved fields and carries a nonzero 32-byte
attempt nonce, the supervisor-observed nonzero PID and process creation
`FILETIME`, the storage root's nonzero volume serial plus all 128
`FILE_ID_INFO` bits, and one closed storage-leaf selector. Production construction
can encode only `YourWallet.KeyAgent.Storage.v1`; `cfg(test)` adds only the exact
CSPRNG test-leaf grammar. Unknown flags, malformed ASCII, nonzero padding,
sentinel identities, and any request slice whose length is not exactly 188 bytes
are rejected. On the live pipe the child must read that fixed frame followed by
exact EOF before decoding, opening the root, or responding. Any suffix, missing
EOF, or read failure is rejected before a success response. After that proof the
child must detach the ambient stdin and stdout entries and close the raw stdin
handle. The raw stdout pipe survives only as a response-capability handle; it is
no longer discoverable through `STD_OUTPUT_HANDLE`.

The parent writes that complete request while the exact-image/LPAC-proven child
still has one verified suspend count. That consuming write closes the sole
parent request endpoint, and only then does the consuming resume transition
release the suspend count for this handshake; no raw-thread or caller-selected
generic resume exists. After sealing its three inherited standard handles as its
first Windows application operation, the child reads the request plus EOF and
must complete that stdin-close/stdout-ambient-detach preflight before decoding
the request or opening the fixed/test leaf beneath the exact OS-rerouted
`LOCALAPPDATA` locator. It validates
the `Packages` / fixed-profile / `AC` shape, derives `TokenUser` and the
AppContainer SID from its own process token, and checks the directory object,
owner, protected two-ACE DACL, inherited Low/`NW` label, and full file identity.

Only an exact match may produce the 88-byte `YWKSRES1` version-1 success frame.
That response echoes the nonce and reports the child's own PID, creation time,
and complete root identity. The first response-write attempt is the child-side
commit point: its result is ignored, as are the following `FlushFileBuffers` and
`CloseHandle` results for the retained response handle. No error may return to
`main` after output begins. After those attempts the child leaves a lexical
startup-only scope, which runs the `Zeroizing` drops for the live request frame,
decoded request, response, and response frame; only the resident stderr boundary
and fixed store bindings escape into a non-alertable `Sleep(INFINITE)` loop with
no further protocol operation. The
parent requires the complete 88-byte frame and exact EOF within the original
startup deadline before decoding and comparing the fields independently. That
exact response-plus-EOF observation is the authoritative protocol proof that the
child response endpoint closed. It then revalidates its no-delete-share root handle, exact
resident-process liveness and root-Job membership, Job context/limits, and
permitted topology before and again after consuming the monotonic one-attempt
lease, so an exited child cannot cross the join merely by producing EOF. A domain-separated
SHA-256 transcript commitment covers the held artifact identity and the exact
request and response frames. The resulting private state retains the running
process, Job, handshake, and root proof, but no startup endpoint. The child
retains sealed stderr and fixed generation-store bindings derived from its
independently opened root in that infinite-sleep loop until the supervisor Job
terminates it. A write/flush/close failure yields no successful parent aggregate:
an incomplete frame or missing EOF fails or times out and the Job tears the child
down. Neither state exposes follow-on runtime I/O, a protected-settings capability, or signing
authority, and neither startup stream is a latent command channel. These exact
EOF checks are repo-local startup-framing proof; signed-artifact trailing-output
and lifecycle evidence remain separate.

The integrated kernel positive uses a persistent test profile/CSPRNG leaf and two
`cfg(test)`-only adapters: the response reader consumes one pinned terse libtest
preamble, and Job topology permits only the fixture plus at most the exact
System32 `conhost.exe`. Production requires response magic at byte zero and one
active Job member. This is not a production fresh-fixed-root or signed-artifact
E2E.

After validating the request/root binding, the child consumes its held root into
one sealed crate-private set of four generation-store roles. Callers cannot
construct or clone a binding and cannot supply a raw path, principal, class,
bound, or frontend selector. The closed tuples are `vault`/Vault/4,194,416,
`nonce-ledger`/NonceLedger/16,777,216,
`signed-candidate-journal`/SignedCandidateJournal/16,777,216, and
`local-settings`/LocalSettings/226. Only the private
`WindowsBackend::open_key_agent` consumes a binding; the public
`WindowsGenerationStore` remains the separate stable-`TokenUser`-only facade.

Every physical file for those roles uses the stable `TokenUser` as owner and a
protected DACL with exactly two explicit allow ACEs in canonical order. The user
mask is `FILE_ALL_ACCESS` (`0x001f01ff`); the exact Key Agent profile mask is
`FILE_GENERIC_READ | FILE_GENERIC_WRITE | DELETE` (`0x0013019f`). The file SACL
must contain exactly one inherited Low/`NW` mandatory-label ACE with only the
`INHERITED_ACE` (`ID`) flag. The backend accepts no other/broad/frontend
principal, extra/reordered/deny/inherited-DACL ACE, mask drift, reparse point, or
hard link. It revalidates thread-impersonation absence and the held/reopened root
with full `FILE_ID_INFO` around each fixed child-path operation. Before replace,
the target must match its original identity-or-absence baseline; afterward the
installed file is rebound to exact bytes, digest, full identity, volume, and
security. The backend security-context hook also bookends every untrusted fault
callback, including both callbacks around rollback-anchor advancement.

The integrated `cfg(test)` zero-capability LPAC path opens all four roles,
commits/loads generation one, closes/reopens, and loads/commits generation two.
For each role it verifies the seven lock/slot/manifest/temporary names. Every
file must return `ACCESS_DENIED` for `WRITE_DAC`, `WRITE_OWNER`, and
`FILE_EXECUTE`, and `PRIVILEGE_NOT_HELD` for `ACCESS_SYSTEM_SECURITY`. The held
root separately proves actual-open `DELETE` as `SHARING_VIOLATION` plus a denied
`AccessCheck`, `FILE_DELETE_CHILD`/`WRITE_DAC`/`WRITE_OWNER` as
`ACCESS_DENIED`, and `ACCESS_SYSTEM_SECURITY` as `PRIVILEGE_NOT_HELD`. The fixture uses in-memory
rollback anchors and synthetic keys/payloads, so it does not prove production
anchor or AEAD-key provisioning.

Parent-side Key Agent, Approval, and Secret Input AppContainer profile
creation/derivation, plus Key Agent `GetAppContainerFolderPath`, share one
process-wide non-reentrant coordinator. It rejects thread impersonation before gate
acquisition and after mutex wait, and immediately before and after every
protected `CreateAppContainerProfile`,
`DeriveAppContainerSidFromAppContainerName`, or
`GetAppContainerFolderPath` call. A successful raw SID or `CoTaskMem` path is
captured by a private RAII owner before the post-call check and is therefore
released even if that check or later validation fails. Except for the binding's
necessary success/error split used to capture a successful allocation, specific
native-error branching and inspection, pointer/SID validity, path decoding and
validation, SID comparisons, and application use occur only after the post-call
check succeeds. These bookends are fail-closed observations rather than an
atomic proof against an impersonation token being installed and removed between
the checks. If that check fails after
a successful `CreateAppContainerProfile`, there is no automatic
`DeleteAppContainerProfile` or rollback; fresh Key Agent provisioning may
already have created the profile and requires recovery. This protocol mints no
profile-registration authority, adds no production reachability, and has no
production `DeleteAppContainerProfile` path. Same-thread reentry and mutex
poison fail closed.

The separate Secret Input child process does not share that parent-side mutex.
Its sole deterministic `DeriveAppContainerSidFromAppContainerName` call uses
child-local pre- and post-call thread-impersonation checks and captures any
successful raw SID in a private RAII owner before the post-call check. Except
for the minimal success/error split needed for that capture, native-error
interpretation, SID-validity checking, and `EqualSid` occur only after the
post-call check succeeds; the owner releases the SID on every failure path.
These bookends are likewise fail-closed observations, not atomic proof that an
impersonation token could not be installed and removed between them. This child
boundary adds no `CreateAppContainerProfile`, `GetAppContainerFolderPath`, or
`DeleteAppContainerProfile` call, profile-registration authority, or new
production reachability. `COMPILED_PARENT_POLICY` remains `None`.

Fresh fixed-profile/root creation now returns a non-launchable pending type;
only a separately prepared type can enter activation, and no direct
pending/candidate conversion mints it. The sole production-compiled prepared
mint is the private sealed existing-install adoption transition. Before the
private pure classifier, a canonical prefix-journal validator authenticates
every fixed record with an installer-owned HMAC-SHA256 key, enforces
phase-specific payloads and the exact `Prepared=1`, `ProfileCreated=2`,
`RootCreated=3`, `Committed=4` sequence, checks every predecessor commitment,
and compares the current commitment/high-water with a separately sealed
rollback-resistant checkpoint carrying independently expected
installation/release identities. The journal `release_identity` is exactly the
whole-release `ReleasePolicy` `ArtifactDigest` accepted by
`ReleaseAttestation`; it is neither the helper-manifest digest nor a Windows
file identity. The helper manifest independently binds the child role, version,
executable hash, and signer, while the retained file handle and full
`FILE_ID_INFO` bind the exact child file object. A changed committed
whole-release identity is `RecoveryRequired`, not an in-place upgrade under this
contract. Because no exclusive installer lease serializes checkpoint,
observation, and post-observation reread, production upgrade orchestration is
not enabled. Rollback, gaps, reorderings, same-generation equivocation,
malformed bytes, and non-canonical unused fields fail closed.
The validator returns an authenticated snapshot. A pure matcher consumes two
matching committed snapshots plus authority-free evidence copied from a
fixed-profile-binding and held-root aggregate; only exact current `Committed=4`
consistency yields stable evidence. Its sole production-code consumer is the
dormant adoption transition, which revalidates the profile binding and same
no-delete-share root before and after matching, mints the prepared value through
one private seal, and retains it inside `VerifiedExistingKeyAgentInstall`.
The implemented dormant release-binding preflights that exact child, performs
one constant-time comparison against the authenticated whole-release identity,
and only then constructs `ArtifactBoundExistingKeyAgentInstall`. Only the
supervisor's private-field seal can split that aggregate for dormant activation;
the resulting install continuity is retained through the dormant and
storage-proven states. It grants no general runtime/signing IPC, installer key,
rollback-anchor, storage/AEAD-key, or protected-settings/lease authority.
The journal validator performs no I/O and has no production key/checkpoint
constructor, journal reader/writer backend, or caller. The adoption transition
and both downstream dormant binding functions have zero production call sites.

A separate dormant `open_existing_fixed_key_agent_storage_root` has zero
production callers and produces only a root capability. Given an
observer-validated `AC` folder and live fixed-profile SID, it hard-codes the
fixed leaf and performs no create, repair, delete, adoption, or recovery. It
rejects impersonation; opens with `OPEN_EXISTING`,
`FILE_FLAG_OPEN_REPARSE_POINT`, and no delete sharing; validates the initial
directory/non-reparse object, local NTFS, exact owner/protected DACL/inherited
Low-`NW` label, and complete `FILE_ID_INFO`; canonicalizes and reopens the path;
and requires the reopened security and identity to match. The capability
privately retains the canonical path and reopened handle, while `revalidate`
checks both the held handle and another canonical reopen. This is neither the
fresh `CreateDirectoryW` pending transition nor the child opener that derives
`LOCALAPPDATA`, `TokenUser`, and the AppContainer SID from its own process.

Production still lacks authoritative profile-registration observation and a
held-aggregate constructor, a production caller for that root opener or the
adoption/binding path, an exclusive installer lease enforcing the
post-observation reread, production installer-key/checkpoint and journal I/O
backends, recovery, and release-activation orchestration. The opener cannot mint
`HeldExistingKeyAgentInstallObjects`, `PreparedKeyAgentProvisioning`,
`VerifiedExistingKeyAgentInstall`, any journal/checkpoint authority,
recovery/activation/signing/RPC/GUI, supervisor ownership, or a Broker+Key Agent
same-release aggregate. Its canonical-path comparison detects mismatch but does
not atomically close the same-user/ancestor race boundary. Production
rollback-anchor and storage/AEAD-key provisioning,
protected-settings/lease authority, authenticated Broker/supervisor topology and
single-instance, and signed immutable artifact/DLL/dependency E2E remain
STOP-SHIP. Exact request EOF and the parent's authoritative response-plus-EOF
check do not provide a runtime channel, signing authority, or release evidence;
there is no generic runtime/signing IPC.
`COMPILED_RELEASE_POLICY` remains `None`.

The crate-private Key Agent offline-lifecycle channel is a separate closed
protocol (`YWOFREQ1`/`YWOFRES1`, version 1). Every request binds a nonzero
request ID, exact sequence, absolute local deadline, declared payload length,
and zero reserved fields, and is read through EOF under a 64-byte cap. One
controller activation accepts at most 64 exact sequential one-shot request
channels and never forgets an identifier during that lifetime; duplicate,
older, skipped, expired, and exhausted requests receive distinct stable codes
and lock decrypted state. Admission converts the bounded wall-clock remainder
to a locally pinned monotonic `Instant`; every sealed helper receives the exact
absolute expiry, and the controller rechecks the monotonic deadline after the
helper returns. That check mints a non-clone capability whose private fields
and constructor exist only in the controller. Every service/session mutation
must consume that exact capability. The capability retains the controller's
trusted clock and rechecks the same pinned monotonic expiry again after
password KDF, derivation, randomness, sealing, or resealing, at the last safe
point immediately before a durable commit, unlock, or pending-state mutation.
An expired or failed final clock sample locks the service without advancing the
durable generation or activating decrypted state.
Only status, 12/24-word create, separate backup-display and confirmation stages,
open, lock, and confirmed-address lookup exist. The create/open/recovery frames
have no payload at all, so the Broker cannot submit a password, mnemonic, or
confirmation answer as proof. Those values must come from crate-sealed Secret
TCB frontend capabilities. Frontends can only acquire zeroizing password or
confirmation input, or present a borrowed recovery view; they never receive the
vault service. Recovery display first returns a non-clone, live-session-bound
`DisplayedRecovery` without changing session state. Only a successful deadline
recheck can consume it into one in-memory challenge, and the later confirmation
command consumes that exact challenge and a fresh opaque binding. Lock, error,
restart, cross-stage use, or replay clears or rejects the pending challenge.
The compiled offline-lifecycle capability is intentionally unavailable until
authenticated one-shot helper adapters and its inherited Windows command channel
are implemented. The Key Agent executable can perform only the separate
storage-startup attempt above. It preflights stdin close and stdout ambient
detachment, attempts the response handle's write/flush/close without returning an
error to `main`, and remains in `Sleep(INFINITE)` under the supervisor Job; it
never serves this offline-lifecycle protocol.

The display projection separately carries origin/provenance, account, network,
chain ID, genesis and rule-set identity, RPC observation digest, operation kind,
and simulation provenance. Transaction displays additionally carry envelope,
nonce, target, native value, gas limit, the exact applicable fee fields,
checked maximum total fee, full bounded calldata and hash, and the complete
canonical access list. Personal-sign displays carry every exact message byte.
No display value is truncated. EIP-712 authorization remains fail-closed until
the native frontend can render the exact structured document.

The fixed wire reply is ordered as magic, version, `decision`, the exact request
digest, and its one-time Approval nonce. Only the digest and nonce echo request
fields.
The Key Agent first creates one crate-private opaque `PreparedApprovalPrompt`,
sampling expiry once and retaining the exact request and its domain-separated
hash. Creation requires a freshly loaded, confirmed protected-settings record.
The prompt carries a non-clone settings lease containing its authenticated
generation, phrase revision, canonical record digest, exclusive owner evidence,
process-instance nonce, and fresh one-time lease nonce. The Windows channel
binds the full request hash (including the local anti-phishing phrase, risk, and
every display field) and held helper identity into a fresh transcript. Immediately
before authorization and signing, the Key Agent consumes the lease once and
freshly reloads the same record; lock, phrase rotation, owner takeover, restart,
record equivocation, or replay rejects the prompt. Authorization then consumes
the same request hash and a non-clone `VerifiedApprovalResponse`. Rebuilding a
shorter-lived request after the UI hold, or substituting any
phrase/display/expiry byte, is rejected. These implemented pieces are not yet a
production orchestration path: there are zero production callers composing
`launch_approval_frontend` through verified response into signing, and there is
no positive signed-handshake E2E. Development builds contain no compiled
release policy and default helper builds exit 78, so the opt-in runtime entry
point cannot be launched by the restricted release path or reach signing. A
challenge expires after at most 120 seconds and can be consumed once; the TCB
clamps it to the browser request's remaining deadline.

## Durable broadcast handoff

Transaction signing is coupled to the concrete encrypted Key Agent journal.
The public signed artifact contains only transaction hash and sender; it is
non-clone and contains no spendable wire bytes. `begin_broadcast` first commits
`Broadcasting`, then returns a non-clone lease whose consuming `submit` method
is the only raw-byte path. Exact local and endpoint hashes commit `Submitted`.
Timeout, transport/RPC error, mismatch, abandoned lease, or crash recovers as
`BroadcastUnknown`; an ambiguous storage commit forces reload and never
releases the nonce.

## Native-host manifest

`extension/native-host/com.your_wallet.native.json.template` is intentionally
not installable. Its extension ID and executable path are placeholders, and the
release validator rejects placeholders. A rendered manifest must contain the
exact host name, `stdio`, one absolute Windows executable path, and exactly one
`chrome-extension://<32 lowercase a-p characters>/` origin.

No installer or registry writer is included. The syntactic validator does not
attest install-path ACLs, Authenticode identity, artifact hashes, registry ACLs,
or private broker pipe security; all remain stop-ship release evidence.
