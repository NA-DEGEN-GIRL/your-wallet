# Solana·Bitcoin dApp 소유 증명(연결 + 메시지 서명) 판정 기록 — 2026-10-31

- 범위: spec.md D22·D25·D26·D27(개정), spec/05 §2.13·§3.6·§4.9(신규)·§2.2·§2.6·§2.8·§3.1·§3.2·§5·§6.1·§6.5, spec/07 §19(신규), spec/08 §17(신규)·§1.2(인스크립션 비목표), spec/04 §2.9·§3.1, spec/02 §5.3(`sol_sites`·`btc_sites`).
- 사용자 결정(정본): Solana·Bitcoin에서 dApp 연결은 **지갑 소유 증명 전용**이다 — 계정 연결과 메시지 서명(Sign-In-With-Solana 포함)만. 거래·PSBT 서명, dApp발 전송 없음. 거래 메서드는 dApp 감지에 필요한 곳에만 두고 항상 4200 + `이 지갑은 Solana/Bitcoin에서 메시지 서명(소유 증명)만 지원합니다`.
- 기준 트리: `46298d7` 위의 커밋 `feat(dapp): Solana/Bitcoin connect and message signing only (ownership proof)`와 이 파일을 담은 문서 커밋.
- 환경: Windows 11 Pro 10.0.26200, Rust 1.95.0 MSVC, `--offline --locked`, Cargo.toml·Cargo.lock 변경 없음(새 크레이트 없음, `secp256k1`의 기존 `recovery` 기능 사용), npm 의존성 0, 확장 권한 불변(`nativeMessaging`, `storage`), 확장 ID 불변 `nnpjlobjgbanccjddghlpaafpohfkeph`, 새 확장 파일 없음(코드는 기존 `src/*`·`popup/popup.html`에 추가).
- 실제 Chrome·실제 dApp·외부 검증기 확인은 하지 않았다(아래 수동 체크리스트).

## 확인하지 못한 것

- 실제 dApp 동작 전부(MS-1–MS-9). 특히 wallet-adapter가 `signTransaction`만 선언한 지갑을 목록에 올리는지, 일부 dApp이 연결 직후 거래 기능을 요구해 화면이 깨지는지.
- Phantom `signIn`의 반환 `address` 형식(PublicKey 유사 객체로 구현, 문자열을 기대하는 dApp은 `toString()`이 base58을 준다).
- sats-connect: 2026-10-31 `secretkeylabs/sats-connect-core` 소스로 요청·응답 형태와 오류 코드를 확인했으나 실제 Xverse 확장과의 차이(예: `wallet_connect`의 `id`, `stacks` 목적 요청 dApp이 Bitcoin만 받아도 동작하는지)는 미확인. JWT 기반 구 sats-connect API는 지원하지 않는다.
- UniSat `signMessage`의 ECDSA를 P2TR 주소로 부르는 dApp은 -32602를 받는다(BIP137에 Taproot 헤더가 없음).
- BIP322 출력은 `smp`/`ful` 접두사가 없는 이전 인코딩이다(최종 BIP 검증기는 접두사 없는 simple을 허용, full의 접두사 없는 형태 해석은 검증기마다 다를 수 있음).
- Wallet Standard에서 실제 Phantom을 숨길 수 없어 phantom 모드에서 "Phantom"이 둘 보일 수 있다(팝업 경고).
