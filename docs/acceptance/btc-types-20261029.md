# Bitcoin 주소 형식(계정별) 수동 체크리스트 — 2026-10-29

- 범위: spec/08 §3.5–§3.6, §6.6–§6.7, §7.2, §10–§12.4의 주소 형식 4종(P2PKH·P2SH-P2WPKH·P2WPKH·P2TR)과 계정 추가·선택, spec/04 §2.6·§2.8 Bitcoin 화면. 자동 시험(`crates/yw-core/src/btc/types_tests.rs`, `crates/yw-app/tests/btc_app_flow.rs` `every_address_type_end_to_end`, `btc_journal_worker.rs` `accounts_are_stored_selected_and_imported_keys_wait_for_the_vault`)이 덮지 않는 실제 노드·인덱서·다른 지갑 확인만 여기서 한다.
- 상태: **미수행**(아래 체크 칸은 모두 비어 있다). testnet4만 쓴다(가치 없음). mainnet 송금은 하지 않는다.
- 환경: 소스 빌드 앱, `bitcoin.network = "testnet4"`, 기본 인덱서 `esplora`(mempool.space testnet4), Core 엔드포인트 `bitcoin:testnet4`. 엔드포인트 URL·토큰은 기록하지 않는다.
- 지갑: 시험용 니모닉만 쓴다(실제 자산이 있는 니모닉 금지). 니모닉 단어는 이 문서에 적지 않는다.

## A. 기존 사용자 호환 (업그레이드)

- [ ] A1. 이 변경 전 앱으로 BTC를 켜고 입금·송금 기록이 있는 데이터 폴더(`%LOCALAPPDATA%\YourWallet\v3` 복사본)를 새 앱으로 연다 → Bitcoin 탭 계정 목록에 `네이티브 세그윗 계정 0 · 네이티브 세그윗 (tb1q…)` 한 행, 잔액·UTXO·활동이 전과 같다.
- [ ] A2. 계정을 추가하지 않은 채 잠그고 다시 열기 → meta에 `btc_accounts`가 생기지 않는다(파일 동작 변화 없음).
- [ ] A3. 탭루트 계정을 하나 더한 뒤 그 폴더를 이전 앱으로 연다 → 이전 앱이 BIP84 계정 0을 그대로 보이고 meta를 다시 저장한 뒤 새 앱으로 돌아오면 탭루트 계정이 남아 있다(모르는 최상위 키 보존, spec/04 §6.6).
- [ ] A4. (A3 상태에서 탭루트 계정으로 송금한 기록이 저널에 있으면) 이전 앱은 BTC 보내기만 멈추고 저널 손상 띠를 보인다 — 새 앱으로 돌아오면 정상(기록 바이트 보존).

## B. 계정 추가·선택 화면

- [ ] B1. `계정 추가` → 선택지가 이 순서로 보인다: `네이티브 세그윗 (tb1q…, 권장)`, `탭루트 (tb1p…)`, `호환 세그윗 (2…)`, `레거시 (m·n…)`, `취소`. 도움말에 형식 설명.
- [ ] B2. mainnet 지갑(조회만, 송금 없음)에서 같은 선택지가 `bc1q…`, `bc1p…`, `3…`, `1…`로 보인다.
- [ ] B3. 각 형식을 한 번씩 추가 → 새 계정이 선택되고 주소 검색(발견)이 돈다. 계정 이름: `탭루트 계정 0`, `호환 세그윗 계정 0`, `레거시 계정 0`, `네이티브 세그윗 계정 1`.
- [ ] B4. 받기 화면: 카드 제목 `{계정 이름} · 받기 주소 0번`, `주소 형식: 탭루트 (tb1p…)` 등, 경로 `m/86'/1'/0'/0/0`·`m/49'/1'/0'/0/0`·`m/44'/1'/0'/0/0`·`m/84'/1'/1'/0/0`. 레거시·호환 세그윗 주소는 대소문자가 섞인 base58 그대로(소문자로 바뀌지 않음), QR을 휴대폰 지갑으로 읽어 같은 주소인지 확인.
- [ ] B5. 승인 창이 열린 동안 다른 계정을 고르면 "Bitcoin 승인이 진행 중이라 계정을 바꾸거나 추가할 수 없습니다".
- [ ] B6. 계정을 바꾸면 잔액·UTXO·활동이 그 계정 것으로 바뀌고, 다른 계정의 진행 중 거래는 계속 추적된다(활동은 계정을 바꿔 돌아왔을 때 갱신됨).

## C. testnet4 송금 (형식마다 1회 이상)

각 행: 파우셋 또는 다른 계정에서 그 계정 받기 주소로 입금 → 확정 후 검증 잔액 반영 → 아래 받는 주소로 소액 송금 → 승인 창 확인 → 확정(6) → 잔돈이 그 계정으로 돌아옴(`own`) → 받는 지갑에서 금액 확인.

| # | 보내는 계정 | 받는 주소 종류 | 승인 창 확인 | 결과(txid 앞 8자) | 확인 |
|---|---|---|---|---|---|
| C1 | 레거시 계정 0 (`m…`/`n…`) | P2WPKH (`tb1q…`) | 서명 계정 `Bitcoin 레거시 계정 0 (m/44'/1'/0')`, 고급 `입력 형식 P2PKH`, txid `서명 후 결정 (레거시 입력)` | | [ ] |
| C2 | 호환 세그윗 계정 0 (`2…`) | P2TR (`tb1p…`) | `Bitcoin 호환 세그윗 계정 0 (m/49'/1'/0')`, 잔돈 `… 이 지갑으로 돌아옴 m/49'/1'/0'/1/0` | | [ ] |
| C3 | 탭루트 계정 0 (`tb1p…`) | P2PKH (`m…`/`n…`) | `Bitcoin 탭루트 계정 0 (m/86'/1'/0')`, 고급 `입력 형식 P2TR` | | [ ] |
| C4 | 네이티브 세그윗 계정 1 (`tb1q…`) | P2SH (`2…`) | `Bitcoin 네이티브 세그윗 계정 1 (m/84'/1'/1')` | | [ ] |
| C5 | 탭루트 계정 0, 입력 2개 이상 | P2WSH (`tb1q…` 62자) | 입력 2개 이상, 노드 사전 검사 통과(BIP341 모든 입력 금액) | | [ ] |
| C6 | 레거시 계정 0, 보내기 최대 | P2WPKH | 잔돈 없음, 수수료율 ≥ 입력값 | | [ ] |

- [ ] C7. 각 송금의 실제 수수료율(mempool.space 거래 화면 sat/vB)이 승인 창 sat/vB 이상이고, vsize가 승인 창 계획 vsize 이하.
- [ ] C8. C3을 하한 수수료로 보낸 뒤 `수수료 올리기`(RBF) → 교체본 확정, 원본 `교체됨`.
- [ ] C9. 한 계정에 진행 중 거래가 있을 때 그 계정의 두 번째 보내기는 막히고(D20), **다른 계정**에서는 보낼 수 있다.
