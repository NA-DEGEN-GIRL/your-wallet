### 2. 고친 것 (전 → 후)

- **1-1 S08 한 번에 RPC 연결**: 전 — S08은 `RPC 설정하기`로 설정 화면에 보내고, 거기서 이름·토큰 두 칸 → `저장` → `네트워크 URL 생성` → 오버레이 `생성` → 네트워크마다 `테스트`를 눌러야 했다. 후 — 엔드포인트가 0개이고 공급자가 QuickNode이면 S08 카드에 "QuickNode 주소" 칸 하나(`ES_PASSWORD`, 주소 전체가 들어가는 폭)와 `연결하기`, 링크 `알케미·직접 입력은 설정에서 ▸`. `연결하기`는 기존 함수만 차례로 부른다: `read_wiping` 뒤 곧바로 칸 비우기 → `quicknode_input`(한 칸에 주소 전체; 빈 값 "주소를 붙여넣으세요.", 형식 오류는 같은 자리에 E-KEY-002) → `set_quicknode` → `save_apikeys`(DPAPI) → 덮어쓰기 없는 `generate`(S08에는 덮어쓸 주소가 없어 T-RPC-GENERATE 없음) → 만든 네트워크 모두 순차 테스트 큐. 결과는 같은 카드에 네트워크마다 한 줄(✓ / ✗는 오류 띠와 §7 문구, 그 행을 여는 링크 / "… 테스트 중")과 "13개 중 11개 작동", ✗가 있으면 대시보드에서 그 체인을 켜고 "모두 테스트"로 다시 확인하라는 안내. rpc.json이 있으면 링크 `rpc.json이 있습니다 — 설정에서 가져오기 ▸`(그 카드로 스크롤). 알케미·직접 입력이면 지금처럼 설정으로 보내는 버튼만. 로그는 `tpl.saved template=quicknode`·`rpc.generated net=…`·`rpc.test net=… result=…`뿐. 시험 `first_setup_connects_quicknode_in_one_step`.
- **1-2 '처음 설정' 체크리스트**: 전 — 제목 "마지막 단계: 블록체인 연결(RPC)" 카드와 `나중에`, 카드 밖 확장 링크, RPC가 있으면 `지갑 열기`만. 후 — 카드 "처음 설정" 하나에 ① 블록체인 연결(RPC)(1-1의 칸, 주소가 이미 있으면 "RPC 주소 n개 · 이번 실행 테스트: 작동 a · 실패 b"와 `RPC 설정 열기`), ② dApp 연결(선택, 둘 중 하나: Chrome 확장 상태 + `설치 방법`(S23, `← 돌아가기`가 S08로) / WalletConnect "Project ID 없음·설정됨" + `설정`(S13)), ③ 첫 입금 시험("실제 자산은 소액으로 받기 → 보내기를 한 번 해 보세요. EVM 탭은 Sepolia 테스트넷으로 시작합니다." + `받기`). `지갑 열기`는 RPC가 없어도 늘 맨 아래. S08에서 연 설정 → 네트워크(RPC)와 S13은 맨 위 링크가 `← 처음 설정으로`(`App::back_row`, 새 플래그 `done_return`)이고 S08로 돌아온다. S08 플래그(`done_imported`·`done_start`·`done_yubikey`·`done_return`·연결 결과)는 `지갑 열기`·`← 메인으로`·잠금에서만 지운다. 가져오기·개인키로 시작 뒤에는 정보 카드 "잔액이 안 보이면": Sepolia로 시작한다는 줄 + `Ethereum 메인넷으로 보기`(네트워크 칩과 같은 `evmChainId` 저장), 계정을 자동으로 찾지 않으니 "내 계정 → 계정 추가"·Solana "다른 경로 스캔"(가져오기만), Bitcoin·Zcash가 꺼져 있으면 그 줄(꺼진 것만).
- **1-3 RPC 공급자 카드**: 전 — `저장`(주) · `네트워크 URL 생성` · `자격 정보 삭제`(늘 켜짐, 확인 없음), 생성은 늘 덮어쓰기 오버레이, 빈 칸이면 E-KEY-004. 후 — 주 `저장하고 RPC 주소 만들기`, 보조 `자격 정보만 저장`(저장 뒤 이 템플릿 대상에 주소가 없으면 "RPC 주소는 아직 없습니다 — “저장하고 RPC 주소 만들기”를 누르세요."), 위험 `자격 정보 삭제`(저장된 것이 있을 때만, 1-6 확인). 덮어쓰기 오버레이는 대상 중 이미 주소가 있는 네트워크가 있을 때만(덮어쓰기 기본 끔 그대로), 없으면 바로 만든다. 칸이 비어 있고 저장된 것도 없으면 E-KEY-004 대신 "위 칸에 엔드포인트 이름과 토큰(또는 주소 전체)을 넣으세요." 생성 안내 "RPC 주소 n개를 만들었습니다. 연결을 확인하는 중입니다 — 결과는 아래 각 행에 나옵니다."(건너뛴 네트워크가 있을 때만 "템플릿 항목이 없는 m개는 직접 입력하세요: …"). QuickNode 도움말에 쓸 체인을 엔드포인트에 하나씩 켜야 한다는 줄, rpc.json이 있으면 카드 첫 줄 안내.
- **1-4 테스트 큐·요약·3상태**: 전 — `테스트`는 네트워크마다 직접, 생성·교체·가져오기 뒤 결과 없음, "테스트 중…"이 빨간 오류 띠. 후 — `App::rpc_tests`(`VecDeque<NetworkId>`, 중복 없음): `RpcEvent::Test` 답이 올 때마다 다음 `RpcJob::Test` 하나만 보낸다(FIFO 작업자가 잔액·보내기 작업을 오래 막지 않게). "네트워크별 RPC 주소" 머리에 "RPC 주소 11/13개 설정 · 이번 실행 테스트: 작동 9 · 실패 1 · 안 함 1", 실패한 네트워크 이름 링크(새 ID 범위 16,720–16,783), `모두 테스트`(도는 동안 꺼진 `테스트 중 3/11`). 자동 테스트: `generate`·`save_replacement`·`finish_rpc_import`가 쓴 네트워크(가져오기 안내도 "연결을 확인하는 중입니다 — 결과는 아래 각 행에 나옵니다."). `rpc_messages`는 3상태(`TestState`: 테스트 중 = 정보, 작동 = 완료, 실패 = 오류 색), 설정 → Bitcoin `Esplora URL` 테스트도 같다. 요청 내용(eth_chainId·getGenesisHash·getblockchaininfo·getblockhash 0, 주소 없음)과 로그는 그대로, EVM 테스트 범위도 넓히지 않았다.
- **1-5 그 네트워크 행으로 바로**: `App::open_rpc_row(network, edit)` — 설정 → 네트워크(RPC)를 열고 그 행의 컨트롤을 보기 안으로 스크롤(`app_scroll::reveal_control`을 `pub(crate)`로), `edit`면 `replace_target`으로 입력 칸(`ES_PASSWORD` 그대로)을 열고 포커스, 아니면 그 행의 `테스트`에 포커스. EVM·Solana·Bitcoin(게이트)·Zcash 탭의 `RPC 설정하기`는 탭별 새 ID로 그 탭의 지금 네트워크를 `edit`로 연다. 설정 탭 `네트워크(RPC)`·`네트워크(RPC) 설정으로`·S08 `RPC 설정 열기`는 그대로 맨 위. 템플릿 자격 정보가 저장되어 있고 그 네트워크에 템플릿 항목이 있으면 열린 칸 위에 "{QuickNode|알케미} 자격 정보가 저장되어 있습니다 — 위 “저장하고 RPC 주소 만들기”로 비어 있는 주소를 한 번에 만들 수 있습니다." S08 ✗ 줄과 요약의 실패 이름은 `edit` 없이 연다.
- **1-6 지우기 확인**: 네트워크 행 `삭제` → `Confirm::RpcUrlDelete(NetworkId)`("RPC 주소 지우기": "{이름} ({NetworkId})의 RPC 주소를 지웁니다. 저장된 주소는 다시 볼 수 없어, 다시 쓰려면 “저장하고 RPC 주소 만들기”({공급자} 자격 정보: 설정됨/없음) 또는 “입력”으로 다시 넣어야 합니다. 이 네트워크에 확정 전 거래가 있으면 주소를 다시 넣을 때까지 상태 확인이 멈춥니다."), `자격 정보 삭제` → `Confirm::TemplateDelete`(끝 "…이미 만든 네트워크별 RPC 주소는 그대로이고, 새 체인 주소를 만들 때 다시 넣어야 합니다."), AI 설명 `키 삭제` → `Confirm::LlmKeyDelete`(끝 "…AI 설명을 다시 쓰려면 키를 다시 넣어야 합니다."). 버튼 `지우기`(위험)·`취소`. 지운 뒤 그 행이나 카드에 완료 띠. 지우는 함수·저장·E-APP-002 처리는 그대로이고 확인만 더했다.

### 2. 고친 것 (전 → 후)

- **2-1 EVM 잔액 바로 다시 읽기**: 전 — Solana는 계정·탭이 바뀌면 다음 틱에 다시 읽었지만 EVM은 네트워크 칩·계정 선택 뒤에도 60초 주기를 기다렸다(그동안 이전 네트워크·계정 기준의 표시). 후 — `App::evm_balances_due`(`next_balance_ms = 0`)를 네트워크 칩(`on_indexed_command`, `save_settings` 다음)과 S08 `Ethereum 메인넷으로 보기`, 계정 선택(`select_account`), 계정이 늘어난 결과(`KeyOutcome::Addresses`·`MnOutcome::Derived` — 첫 복구 단어와 추가 복구 단어 —, 가져온 EVM 키 두 경로, meta 다시 읽기로 오는 YubiKey 계정), HyperCore 카드의 `HyperEVM에서 Core로 이동`(`evmChainId` 저장), 추적 결과에 `Included`·`Finalized`·`Dropped`가 있을 때, 그리고 그 네트워크의 RPC 테스트가 작동했을 때 부른다. S10에서는 `evm_tick`이 다음 틱(≤ 250 ms)에 `refresh_balances`를 부른다. 시험 `chip_and_account_changes_read_balances_at_the_next_tick`.
- **2-2 토큰 잔액의 소유자**: 전 — `BalanceSnapshot`의 토큰 잔액은 작업을 보낼 때의 선택 계정 것인데, 계정을 바꾸면 다음 읽기 전까지 새 계정의 토큰 잔액처럼 보였다(토큰 카드, "토큰: …" 줄, S11 보유량, `{기호} 보내기`). 후 — `BalanceSnapshot.token_owner`(작업자가 `RpcJob::Balances`의 `token_owner`로 채움); `App::token_balance`는 그것이 지금 선택한 계정이 아니면 없음 — 토큰 카드 "잔액 알 수 없음", 선택 계정 카드의 "토큰: …" 줄 빠짐, S11 자산 라디오 "· 잔액 모름", `{기호} 보내기` 꺼짐. 2-1 덕분에 새 계정의 값은 다음 틱에 온다. 시험 `token_balances_of_another_owner_are_unknown`.
- **2-3 잔액 세 상태와 RPC 실패 안내**: 전 — 큰 잔액 아래 "블록 N 기준 · 갱신 실패 E-RPC-003", 상태 줄 "오류 E-RPC-003"으로 코드만 보였고 무엇을 해야 하는지 없었다; 값이 없으면 "잔액을 아직 읽지 못했습니다. RPC 연결을 확인하고 새로고침하세요."뿐. 후 — `BalanceState.updated_unix_ms`·`SolUi::balance_at`에 결과를 받은 시각을 남기고 큰 잔액 아래를 세 상태로: 결과가 아직 없으면 "잔액을 불러오는 중…", 성공이면 "블록 N 기준 · HH:MM 갱신"(Solana는 블록 번호가 없어 "… lamports · RPC finalized 기준(참고) · HH:MM 갱신"), 실패이면 네트워크 카드에 '오류' 띠 하나 — 그 코드의 §7 전체 문구(`ErrorCode::text`)에 이전 값이 있으면 "아래 잔액은 블록 N에서 마지막으로 읽은 값입니다."(Solana "HH:MM에") — 와 버튼 `이 네트워크 RPC 테스트`(배치 1과 같은 큐의 `RpcJob::Test`, 결과는 같은 카드에 3상태 띠, 작동하면 다음 틱에 다시 읽음)·`RPC 설정 열기`(`open_rpc_row(network, false)`). 선택 계정 카드는 "잔액을 읽지 못했습니다 — 위 네트워크 카드의 안내를 보세요."이고 이전 값은 흐리게(새 `Item::DisplayMuted`) 둔다. 상태 줄은 "오류 E-RPC-003 · 인증 거부"(`ErrorCode::short_name`, E-RPC-001–010, spec/04 §7 표에 "짧은 이름"). 띠에는 네트워크 이름만(URL·호스트 없음, §1.9). 주소 없음(U17)과 차단 상태는 그대로이고, 알 수 없는 체인(E-APP-009)은 "불러오는 중"에 머물지 않고 실패 띠로 보인다. 새 시험 없음(문구를 단언하던 시험도 바뀌지 않았다).
- **2-4 Solana 메인넷 띠 한 겹**: 전 — `main_screen`의 Solana 분기가 T-MAINNET을 넣고 `sol_main_screen`의 `sol_cluster_banner`가 또 넣어(11-08 회귀) 두 겹. 후 — 분기의 세 줄을 지워 `sol_cluster_banner` 하나만. S11·S12는 원래 한 겹. 시험 `backup_discard_mainnet_and_done_texts`에 Solana mainnet S10·EVM 메인넷 S10(1, 999)의 T-MAINNET 띠가 정확히 1개인지 세는 단언을 더했다.
- **2-5 같은 이름의 계정 구분**: 전 — 복구 단어마다 첫 계정이 "계정 1"(Solana "Solana 1")이라 목록 밖(선택 계정 카드, S11, S12, 활동)에서는 어느 것인지 알 수 없었고, 첫 복구 단어 계정의 경로만 "m/44'/60'/0'/0/i"였다. 후 — 복구 단어가 둘 이상이면 그 자리들의 이름에 `mnemonic_tagged`("계정 1  [복구 단어 2]")를 쓴다(EVM `evm_account_title`·`evm_pref_title`, Solana `sol_title`; Solana S11은 이전부터). 첫 복구 단어 계정의 경로 줄은 "{첫 복구 단어 라벨} · m/44'/60'/0'/0/{i}"(`evm_path_text`, S10·S12). 새 계정의 기본 이름은 모든 복구 단어를 통틀어 겹치지 않는다: EVM "계정 {지금 있는 “계정 N” 중 최댓값 + 1}"(`Meta::next_evm_number`, 가져온 키·YubiKey 계정 이름도 센다), Solana "Solana {…}"(`Meta::next_sol_label`) — `KeyOutcome::Addresses`(앱이 번호를 `workers::key::new_account(index, number, address)`에 넘긴다), `MnOutcome::Derived`, Solana `계정 추가`·추가 복구 단어 계정·스캔에서 더하기, key worker의 meta 맞추기(추가 복구 단어의 첫 EVM·Solana 계정; 문서 전체와 그 자리에서 만든 항목을 센다). 이미 저장된 이름은 그대로. 각 복구 단어의 첫 계정에서 `숨기기`가 꺼져 있으면 도움말 "각 복구 단어의 첫 계정(…/0)은 숨길 수 없습니다."(EVM·Solana). 새 시험 없음.
- **2-6 EVM 토큰 보내기의 단위와 수수료**: 전 — 금액 칸 라벨 "금액"(단위 없음), 도움말 "'최대'는 수수료를 뺀 잔액 전부입니다."가 토큰에도 나왔고(토큰은 수수료를 빼지 않는다), 수수료를 낼 ETH가 없으면 "잔액이 부족합니다(수수료 포함)"만 보였다. 후 — 라벨 `금액 ({기호})`, 도움말은 기본 자산 "'최대'는 수수료를 뺀 잔액 전부입니다." / 토큰 "'최대'는 이 토큰 잔액 전부입니다. 수수료는 {네이티브}로 따로 냅니다.", 기본 자산 라디오에도 보유량("SepoliaETH · 1.25" / "· 잔액 모름"), 토큰이면 수수료 줄 "예상 최대 수수료: {x} {네이티브} (보유 {y} {네이티브})", `check_funds`의 E-INP-012가 네이티브 수수료 부족이면(토큰 금액 ≤ 토큰 잔액) 그 띠 아래 "수수료를 낼 {네이티브}이(가) 부족합니다 — 이 계정에 {네이티브}을(를) 먼저 받으세요." §7 문구·코드·검사·검토·승인 규칙은 그대로. 새 시험 없음.
- **2-7 활동 목록 맞추기**: 전 — Zcash 행만 `Field` 한 줄("보냄 X ZEC" | "상태 · 수수료 n zats · 받는 주소 … · 만료 높이 …", 시각 없음), 받는 주소가 EVM·Solana는 도움말 글자, Bitcoin·Zcash는 제각각, 주소록·내 계정 주석은 EVM만, Ethereum·Sepolia에는 `탐색기 링크 복사`가 없었다. 후 — Zcash 행은 "{YYYY-MM-DD HH:MM} · 보냄 {X} ZEC"(`signed_at_ms`, 로컬 시각) / "상태: …"(만료 높이는 미확정일 때만) / "받는 주소"와 `Mono` 4자 묶음 전체 / "수수료 0.0001 ZEC"(zats를 ZEC로) / txid. 받는 주소 줄은 모든 체인에서 "받는 주소{주석}" + `Mono` 묶음이고, Solana·Bitcoin에도 표시 전용 " → 주소록: {이름}"·" → 내 계정: {라벨}"(Zcash는 주소록이 없어 내 계정만). yw-core `chain.rs` 탐색기: Ethereum 메인넷 `https://etherscan.io`, Sepolia `https://sepolia.etherscan.io`, HyperEVM은 spec에 공식 탐색기가 없어 그대로 없음(spec/03 §1 표). `탐색기 링크 복사`는 지금처럼 `{explorer}/tx/{hash}`를 복사만 한다(§2.14). 활동 주소에 복사·선택 버튼을 두지 않는 규칙 그대로, EVM 외 활동 접기는 하지 않았다. explorer 없음을 단언하던 시험은 없었다.
- **2-8 HyperCore 카드 접기**: 전 — Sepolia·Base 같은 체인을 볼 때도 HyperCore 카드(빨간 메인넷 띠, 라디오, 버튼 6개)가 늘 펼쳐져 화면을 차지하고, 위 EVM 테스트넷 띠와 함께 띠가 둘이었다. 후 — `hc_foldable`: 선택한 EVM 체인이 999·998·42161·421614가 아니고, 선택 계정의 HyperCore 활동이 서명 중·전송 중이 아니고, 이번 실행에서 펼친 적이 없으면 접힌 카드 — 배지와 "Hyperliquid HyperCore 메인넷 · 계정 가치 1,234.56 USDC · 현물 3종"(불러오기 전·불러오는 중·실패는 그 상태 한 줄, 테스트넷은 "HyperCore 테스트넷"), 링크 `펼치기 ▸`. 접힌 카드에는 동작 버튼도 띠도 없다. 펼치면 지금 카드 그대로에 `접기 ▴`. 동작 버튼을 그리는 곳에는 언제나 네트워크 띠도 그린다. 60초 잔액 읽기는 그대로, 펼친 상태는 메모리에만(`HcUi::unfolded`). 링크 ID 13,494–13,495(HyperCore 범위, `ui::command_ids`에 등록), spec/11 §8에 한 줄. 시험 `the_hypercore_card_folds_next_to_other_chains`(기존 `card_activity_is_the_selected_accounts`는 HyperEVM에서 보도록 고쳤다).
- **2-9 Bitcoin 수수료 미리 보기**: 전 — 빠름·보통·느림이 무엇인지(대기 시간·sat/vB) 몰랐고, 수수료 하한·예상 수수료는 `검토`(계획) 뒤에야 보였다. 후 — 읽기 전용 `BtcRpcJob::FeeQuote { job, target, chain }`: `Refresh`와 같은 세션 체인 확인(`ensure_chain`) 뒤 `get_mempool_info`(하한)와 `estimate_smart_fee` 2·6·24(economical)를 기존 cap·파서로 읽어 `BtcRpcEvent::FeeQuote { floor, rates: [Option<FeeRate>; 3] }`. 주소를 보내지 않고 계획·승인·UTXO 예약도 없다. 보내는 때: 폼을 열 때, 사용자 `새로고침` 때, 견적이 60초보다 오래된 상태에서 수수료 라디오를 바꿀 때. 라디오 "빠름 · 약 20분 · 12 sat/vB" / "보통 · 약 1시간 · 8 sat/vB" / "느림 · 약 4시간 · 3 sat/vB"(하한보다 낮은 추정은 하한 — `choose_fee_rate`와 같다, 추정이 없으면 "· 추정 없음", 불러오는 중이면 줄 "수수료 추정을 불러오는 중…"). 금액과 받는 주소가 유효하면 "예상 수수료 약 1,692 sats (0.00001692 BTC) — 입력 1개·출력 2개(받는 사람·잔돈) 기준입니다. UTXO를 여러 개 쓰면 늘어납니다. 실제 수수료는 검토에서 다시 계산해 승인 창에 보입니다."(vsize = `estimate_weight_with(계정 input_weight, 1, [받는 주소 spk, 잔돈 spk])`, 로컬 계산), 상한(500 sat/vB·0.005 BTC)을 넘으면 주의 "이 수수료율은 상한을 넘어 검토 뒤 수수료(sats)를 직접 입력해야 합니다." "수수료 하한 …" 줄도 견적의 하한으로 검토 전에 채운다. "주소 종류: P2WPKH" → "주소 종류: 네이티브 세그윗 (P2WPKH)"(다른 형식도 쉬운 이름 먼저; 승인 창의 `type_label`은 그대로). `검토`(Prepare)는 지금처럼 추정과 하한을 새로 읽고 견적을 쓰지 않는다. 상한·typed-fee 해제·승인 창 표시 그대로. spec/08 §8.2. 새 시험 없음(기존 파서·cap을 다시 쓴다).
- **2-10 스크롤**: 전 — 체인 탭을 바꿔도 이전 탭의 스크롤 위치가 그대로라 새 탭의 네트워크 띠가 화면 밖일 수 있었고, `← 메인으로`·`취소`·오버레이 `취소`는 늘 맨 위로 돌아갔고, DPI가 바뀌면 같은 픽셀 값이 다른 위치였다. 후 — 탭 클릭과 Ctrl+1–4(`TAB_EVM`, `sol/btc/zec_select_tab`)는 `tab_top`: 떠나는 탭의 위치를 적고 scroll 0, `stop_scroll`. `app_scroll::ScrollMemory`가 이번 실행 동안 S10 탭별·설정 구역별·S08·S13·S14의 마지막 위치(DIP)를 기억하고, 돌아오는 길(`App::return_to`: `← 메인으로`, S23 `← 돌아가기`, `← 처음 설정으로`, 보내기·수수료 올리기·S-HC `취소`)로 들어오면 내용 높이로 잘라 복원한다. 확인 오버레이는 아래 화면의 위치를 적어 두었다가 `취소`나 확인 뒤 그 화면으로 돌아오면 거기로. 새로 들어가는 화면, 오버레이, 탭 전환, 잠금 뒤에는 맨 위(잠그면 기억을 지운다). `Msg::DpiChanged`는 scroll에 새 DPI / 옛 DPI를 곱한다(마지막 배치의 DPI를 기억). 위험 표시는 그대로이고 탭에 들어가면 띠가 먼저 보인다. 시험 `a_chain_tab_opens_at_its_top`.
- **2-11 F5·Ctrl+,·Esc와 설정 구역 기억**: 전 — 주 창에는 Ctrl+L·Ctrl+1–4·탐색 키만 있었고 Esc(`IDCANCEL`)·Enter는 아무것도 하지 않았으며 `설정`은 늘 `보안`으로 열렸다. 후 — 관찰자(VK_L 옆)가 F5와 Ctrl+,를 `WM_YW_SHORTCUT`(`events::Shortcut`)으로 post. ### 3. 남긴 것과 이유·대안

- **D1 `{기호} 보내기`는 숨기지 않고 끈다**(2-2): 제안은 "잔액 > 0일 때만 보임 → 숨는다"였지만 지금 규칙(spec/04 §2.6, Solana 토큰 카드와 같음)은 링크를 늘 그리고 잔액 > 0일 때만 켠다. 소유자가 다른 스냅샷이면 잔액이 없음이 되어 링크가 꺼지므로 누를 수 없다는 결과는 같고, Solana 카드와의 일관성을 지켰다.
- **D2 Ctrl+,는 `설정` 버튼이 보일 때만**(2-11): F5와 같은 "그 컨트롤이 보이고 켜져 있을 때 누른다" 경로라 상단 막대가 있는 S10에서만 동작한다. 다른 화면에서 설정으로 뛰면 입력 중인 폼을 떠나게 되어 이번에는 넓히지 않았다.
- **D3 Bitcoin 계정 이름**(2-5): 0부터 세는 기본 이름과 이름 바꾸기는 BTC meta에 필드가 필요해 하지 않았다(항목 범위). Bitcoin 활동의 " → 내 계정: …"은 지금 계정 이름("네이티브 세그윗 계정 0")을 쓴다.
- **D4 Solana에는 블록 번호가 없다**(2-3): Solana 잔액 응답에서 slot을 받지 않아 성공 줄은 "… RPC finalized 기준(참고) · HH:MM 갱신", 실패 띠의 끝은 "아래 잔액은 HH:MM에 마지막으로 읽은 값입니다."로 바꿔 썼다.
- **D5 수수료 미리 보기의 범위**(2-9): 수수료 올리기 폼과 Zcash 예상 수수료는 하지 않았다(항목 범위). 보내기 최대는 UTXO 여러 개·잔돈 없음이라 "입력 1개·출력 2개" 예상이 맞지 않아 예상 수수료 줄을 보이지 않는다.
- **D6 스크롤을 기억하는 화면**(2-10): 목록의 화면(S10 탭별·설정 구역별·S13·S14)과 `← 처음 설정으로`가 돌아가는 S08만 기억한다. S11·S12·S-HC 같은 폼은 늘 맨 위에서 연다. S17의 `취소`는 돌아오는 길 목록에 없어 그대로 맨 위다.
- **D7 다중 모니터·혼합 배율의 실기 확인**(2-12): 이 PC에서는 순수 함수 시험과 단일 모니터 실행만 했다. 다른 DPI 모니터로 옮긴 위치의 복원(같은 사각형 두 번 적용)은 다음 수동 확인 때 본다. 승인 창 배치는 배치 3에서 다룬다.
- **D8 알림 기록·띠별 닫기·진단 요약 복사**(2-13): 항목대로 하지 않았다.
- **D9 화면 투어**: 바뀐 장면만 다시 찍었다. 02·08·24·25·32는 스크롤 막대가 늘 보이기 전(960 폭)의 사진이고 29는 배치 1 이전의 스크롤 위치지만 내용이 같아 이번에도 다시 넣지 않았다. 12·13·22·23·39·42·44·09는 경과 시간·카운트다운 같은 시각 값만 달라 넣지 않았다.

### 2. 고친 것 (전 → 후)

- **3-1 메인넷 배지와 넘친 배지**: 전 — 메인넷 알약은 테스트넷과 같은 흰 알약이라 노란 머리의 테스트넷 창보다 덜 눈에 띄었고, 첫 줄에 들어가지 않는 배지는 `break`로 말없이 버려졌다. 후 — `app_approval::layout_badges`(순수 함수)가 알약 폭을 재서 머리 폭에 맞춰 여러 줄로 놓고 `header_height`에 줄 수 × 30 DIP를 더한다. 순서는 `badge_rank`: 네트워크(메인넷/테스트넷) → 출처 위험(punycode·http) → 호환 모드·WalletConnect 세션 → 사용자 체인 → YubiKey·Verify(서명 창·연결 창·WalletConnect 연결 창 모두). T-MAINNET 알약(EVM·Solana mainnet·HyperCore 메인넷)은 `DANGER_ACCENT`로 채우고 흰 굵은 글씨(고위험 태그와 같은 색), 그 배지가 있으면 머리 맨 위에 4 DIP `DANGER_ACCENT` 줄. 테스트넷·사용자 체인·기타 알약과 Bitcoin 메인넷의 빨간 머리는 그대로. 시험 `every_header_badge_is_placed_and_the_mainnet_pill_is_red`(520 DIP, 배지 6개). spec/04 §3.2.
- **3-2 승인 창을 주 창 모니터 안에**: 전 — `Window::center_on`이 `SWP_NOSIZE`로 위치만 옮겨, 150 % 배율의 1920×1080·세로 1080×1920 모니터에서 승인 창(약 1,250×1,110 px)의 `승인`이 화면 밖일 수 있었다(이 PC는 AppliedDPI 144, 모니터 4대). 후 — 창을 먼저 대상 모니터로 옮겨 `WM_DPICHANGED`가 그 모니터 DPI로 크기를 바꾸게 하고, 바깥 크기를 그 작업 영역 안으로 줄여 가운데에 둔다(최소 520×460 DIP는 `WM_GETMINMAXINFO`). 승인 창만 쓰는 함수이고 unsafe는 yw-win 안에만. 무장 지연·클릭 관통 방지·TOPMOST·버튼 위치 계산은 그대로. 수동 체크리스트 UI-M3-14(spec/04 표, docs/acceptance/m3-20261027.md)에 "주 창을 1080p·세로 모니터에 두고 승인 창의 승인 버튼이 보이는지"를 더했다. 새 시험 없음.
- **3-3 하단 막대의 다음 할 일**: 전 — "남은 시간 … · 대기 중인 다른 요청 n건 · {상태} · {다음 할 일}"이 흐린 한 줄(`DrawFlags::LINE`)이라 좁은 창·대기 요청·재시뮬레이션 실패가 겹치면 다음 할 일이 잘렸다. 후 — `bar_state`가 다음 할 일(`next_step`)을 떼고, `bar_layout`(순수 함수)이 상태 줄 "남은 시간 m:ss · 대기 n건 · 상태 문구"(길게 누르는 동안 "{0.0}초")를 줄바꿈하고 다음 할 일을 `TEXT` 10pt 굵게 버튼 왼쪽 칸에 2줄까지, 그 칸이 260 DIP보다 좁으면 버튼 위 자기 줄에 둔다(좁은 창은 다음 할 일이 없어도 두 줄을 비워 두어 무장·누르기 때 내용이 움직이지 않음). 막대 높이는 줄 수로 다시 계산하고(최소 96 DIP) 높이가 바뀌면 창 전체를 다시 그린다. 상태 문구가 다음 할 일과 같은 지시를 담으면(T-SIM-CHANGED·T-SIM-RESIM-FAILED) 다음 할 일이 보이는 동안 사실만("다시 실행한 시뮬레이션이 성공하지 못했습니다"). 남은 시간 30초 이하는 주의 색. 버튼은 오른쪽 아래 고정, `can_approve`·무장·누름 간격·2초 누르기는 그대로. 시험 `the_whole_next_step_fits_a_narrow_bar`(520 DIP, 대기 3건, 재시뮬레이션 실패). spec/04 §3.2 하단 행·§7.
- **3-4 승인·permit 요약**: 전 — approve는 "컨트랙트를 호출합니다: 토큰 사용 승인…"과 토큰 컨트랙트 주소, permit은 "'토큰 사용 허가 서명 (permit)'에 서명합니다(EIP-712)…"로 누구에게 얼마나가 없었다. 후 — `approval_view::summary_value`만 고쳐 표시 모델에서 문장을 만든다(11-10 transfer 요약과 같은 방식, digest·등급 그대로). 요약 아래 주소는 권한을 받는 주소(spender·operator·API 지갑)와 그 주석. approve·increaseAllowance "{네트워크}에서 아래 주소에 {토큰} 사용 권한을 줍니다: {금액|무제한}.", setApprovalForAll(true) "…이 컬렉션 NFT 전체를 옮길 권한을 줍니다.", PermitSingle "…아래 주소가 {금액}을(를) {허용 만료}까지 쓸 수 있게 하는 서명입니다."(PermitBatch "토큰 n종"), EIP-2612·DAI permit "…가져갈 수 있게 하는 서명입니다. 거래 없이 서명만으로 쓰일 수 있습니다.", Permit2 즉시 이체 "…바로 가져갈 수 있게 하는 서명입니다.", Hyperliquid ApproveAgent "…아래 주소(API 지갑)에 내 계정으로 주문·취소할 권한을 줍니다.", 금액 0·lockdown(첫 spender)·approved=false "…아래 주소의 권한을 거둡니다(승인 해제)." 값은 `0x0104` 호출 인수와 typed data 구조화 필드에서만 읽고 찾지 못하면 이전 문장. 시험 `permission_summaries_name_who_gets_what`(표 형식: approve 무제한, EIP-2612, PermitSingle, setApprovalForAll, 승인 해제의 문장과 요약 주소). spec/04 §3.2 요약 행.
- **3-5 서명 창 배치와 메시지 창 소음**: 전 — H01·M04·S09·W08·P03이 각자 "정보" 상자로 "참고" 구역을 만들어 핵심 정보 앞을 밀었고, 메시지 창은 원문이 해석한 로그인 필드보다 먼저였다. 후 — `signing_view`와 그리기만: (1) 요약이 받는 주소 문장이면 E28·E29는 요약 카드 바로 아래 정보색 상자, 아니면 "참고" (2) H01·M04·S09·W08·P03은 상자·태그 없이 요약 카드 맨 아래 9pt 흐린 한 줄 "참고: {문구} · …"(C04는 합치지 않음) (3) 나머지 "참고"는 "핵심 정보" 다음·"자세히" 앞 (4) EVM "자산 변화" 카드 끝 "수수료: 예상 {0x0121} (최대 {0x0120})"(예상이 없으면 최대만; 두 필드는 아래에 다시 나오지 않음) (5) 제목 동작 "로그인 요청 (SIWE)·(SIWS)"이면 핵심 정보 안에 소제목 "로그인 내용"(해석 필드) 다음 "메시지 원문"(둘 다 펼침) (6) 바로 뒤가 실제 줄바꿈인 `[U+000A]`만 `MUTED`(다른 `[U+XXXX]`는 `ESCAPE_TEXT`) (7) 머리 값이 공백 없는 SOL·BTC 주소 한 줄이면 4자 묶음(SOL 가운데·BTC 앞뒤 6자 굵게, 글자 그대로) (8) `SIWB_MARKER`가 있는 Bitcoin 메시지는 "{네트워크}에서 {도메인} 사이트 로그인(Sign-In with Bitcoin) 메시지에 서명합니다. 거래 서명이나 전송은 하지 않습니다." 정보 줄 셋 이상을 하나로 묶지 않았다. 시험 `restating_lines_join_the_summary_card`(M04가 상자가 아니라 요약 카드 줄, 문구는 남음, 구역은 "핵심 정보"만). spec/04 §3.2·§3.3.
- **3-6 연결 창의 계정과 사이트 기본 계정**: 전 — EVM 연결 창 행은 라벨·주소뿐이라 복구 단어가 여럿이면 같은 "계정 1"이 구분되지 않았고, Solana·Bitcoin 창은 새 사이트에 그 탭의 계정이 아니라 첫 계정을 골랐으며, S13에는 사이트가 쓰는 계정이 없었다. 후 — EVM 행은 "라벨, 흐린 둘째 줄 {출처 · 경로}(`account_rows` 넷째 칸), 주소"(Solana·Bitcoin 창도 같은 꼴). 복구 단어가 둘 이상이면 복구 단어 계정의 표시 이름은 "{라벨} ({복구 단어 라벨})"(`App::mnemonic_named`, 괄호 — `[내 계정: …]` 안에서 대괄호가 겹치지 않게)이고 `own_accounts`가 이 이름을 돌려주어 연결 창·S13 카드·WalletConnect 세션 카드·"사이트가 기본으로 쓰는 계정" 줄·`ChainFacts::own_accounts`(머리와 주소 주석의 `[내 계정: …]`)가 같이 쓴다(Solana dApp 행도). 주소 비교·grant는 그대로. Solana·Bitcoin 창의 새 사이트 기본 선택은 그 탭에서 고른 계정(백업 확인 전·공장 PIN 계정은 빼는 규칙 유지, 기존 grant 우선). S13 EVM 카드의 "볼 수 있는 계정" 아래 "사이트가 기본으로 쓰는 계정: {라벨}"(grant의 첫 계정). 승인은 그대로 사용자가 한다. 비슷한 주소 사이트 경고·S13 카드 묶기·계정 바꾸기는 하지 않았다. spec/05 §4.2·§4.9, spec/04 §2.9. 새 시험 없음(문구를 단언하던 시험은 바뀌지 않았다).
- **3-7 YubiKey 지갑의 백업 문구**: 전 — 복구 단어 없는 YubiKey 지갑에 "개인키로 시작해 복구 단어가 없습니다… 모든 계정은 '가져온 키'"가 나왔고, 설정 → 보안에는 백업 현황이 아예 없었다. 후 — `key_only()`는 그대로 두고 카드 기록이 있으면 `내 계정`·`내 Solana 계정` 도움말 T-ACCOUNTS-YUBIKEY "보내기·받기에 쓸 계정을 고르세요. 이 지갑은 복구 단어를 저장하지 않습니다. [YubiKey] 계정의 키는 카드 안에만 있고, 백업은 등록할 때 적은 복구 단어입니다(복구 단어 없이 연결한 키는 그 카드와 같은 키를 가진 백업 카드)." + 가져온 키가 있으면 "[가져온 키]는 원래 개인키가 백업입니다."(`App::accounts_help`). 복구 단어 지갑에 YubiKey 계정이 있으면 T-ACCOUNTS-BACKUP 끝에 "[YubiKey] 계정은 YubiKey를 등록할 때 쓴 복구 단어로 복구됩니다(이 지갑의 복구 단어와 다를 수 있음)." 설정 → 보안 "복구 단어·개인키" 카드는 복구 단어가 없어도 "백업 현황 — 이 지갑을 다시 열려면"(`backup_status_all`)을 그리고(개인키 보기 버튼 그대로), YubiKey 줄은 키마다 "· EVM 계정 0 — YubiKey #12345678 · 복구 단어로 다시 만들 수 있음" / "· EVM 계정 (카드 키 1) — 복구 단어 없음, #12345678에만 있음 ⚠"(다른 카드에도 있으면 "#…·#…에 있음"). 같은 줄을 잠금 해제 상태의 S22 맨 위에도. 초기화 문구(설정 → 보안 "지갑 초기화" 도움말, T-RESET-DONE, T-WAIT-STALLED)는 "복구 단어·원래 개인키, 또는 YubiKey(“YubiKey 연결하기 (복구 단어 없이)”)가 필요합니다", S18은 "복구 단어가 없어 “계정 추가”는 없습니다 — 나중에 설정 → 복구 단어에서 더하면 생깁니다." 문구만. 새 시험 없음(문구를 단언하던 시험은 바뀌지 않았다).
- **3-8 카드 단계 안내**: 전 — PIN 제출 뒤 "YubiKey가 깜박이면 터치하세요 (15초 안에)."와 취소 문구가 늘 머리 띠(보내기 폼은 아래에 있음)에 떴고 서명이 끝나도 남았으며, W11은 카드가 없거나 다른 프로그램이 쥐고 있어도 PIN을 넣은 뒤에야 알렸다. 후 — `app_card`가 터치 안내 "PIN을 확인하는 중… YubiKey가 깜박이면 15초 안에 터치하세요"(BTC·ZEC "YubiKey가 깜박일 때마다 터치하세요 — 모두 {n}회(입력마다 한 번)")와 W11 취소 문구를 그 단계를 연 보내기 폼(EVM S11, Solana·Bitcoin 보내기와 수수료 올리기, Zcash 보내기 카드, S-HC)의 `검토` 위 줄에 둔다(그 폼이 지금 화면이 아니면 — dApp 요청·가속·취소 — 머리 띠; `on_signed`와 같은 규칙). S-HC는 카드 서명 동안 메인으로 넘어가지 않아 그 줄이 보인다. 카드 결과(서명·실패·취소·PIN 다시 묻기·잠금)가 오면 터치 안내를 폼과 머리 띠에서 지운다(`CardUi::notice`). `on_yk_counters`는 `CounterTarget::Key`의 `Err`를 버리지 않고 W11 상세 줄에 PIN 전 보인다: 카드 없음 "YubiKey #{n}을(를) 찾지 못했습니다 — 연결한 뒤 PIN을 입력하세요", 점유 "다른 프로그램(gpg-agent 등)이 YubiKey를 쓰고 있습니다 — 그 프로그램을 닫은 뒤 확인을 누르세요", 다른 카드 "연결된 YubiKey(#{m})에는 이 키가 없습니다 — #{n}을(를) 연결하세요"(꽂힌 카드가 하나면 작업자가 읽기만으로 그 일련번호를 가져온다). W11 안내의 겹치던 두 문장은 "1. YubiKey #{n} 연결 → 2. PIN 입력 후 확인 → 3. 깜박이면 15초 안에 터치 (승인 뒤 120초 안에)". PIN 버퍼 이동, 제출하면 W11이 닫히는 수명, 120초, 공장 PIN 거부, 캡처 제외 그대로. 시험 `the_touch_prompt_is_gone_once_the_card_answers`(S11 폼 줄 → 서명 뒤 없음, dApp 요청의 머리 띠 → PIN 다시 묻기 뒤 없음). spec/10 §9.2.
- **3-9 공장 기본 PIN 카드는 폼에서 미리 막기**: 전 — 카드가 `hw_accounts.defaults`인 YubiKey 계정은 폼·검토·승인을 다 마친 뒤 카드 단계에서야 거부되었고, 빨간 T-CARD-FACTORY-PIN과 노란 T-YK-PIN-NEEDED가 함께 떴다. 후 — U7(백업 확인 전 계정)과 같은 길로 `card_begin`의 판정(`App::card_on_defaults(role)`)을 앞당긴다: 선택 계정 카드(EVM·Solana·Bitcoin)와 S11·Solana·Bitcoin·Zcash·S-HC 보내기 폼에 주의 띠 "YubiKey #{n} PIN 설정 전 — 이 계정은 받기만 되고, 보내기·서명은 PIN을 바꾼 뒤에 됩니다."와 `PIN 설정`(설정 → YubiKey의 그 카드 PIN 카드)을 보이고 `검토`를 끈다. 연결 창 행에 "[YubiKey #{n} PIN 설정 전 — 서명 불가]", 새 사이트 기본 선택에서 뺀다. dApp 서명 요청(EVM·Solana·Bitcoin)은 `site_preflight`에서 창 없이 4100으로 거절하고 알림 "{사이트}의 서명 요청을 거부했습니다: YubiKey #{n}의 PIN이 아직 공장 기본값이라 서명하지 않았습니다 — 설정 → YubiKey → PIN 설정". `card_begin`·`card_submit`의 검사는 마지막 방어선으로 남기고, 거부될 때는 노란 띠(버튼 포함) 하나만. 카드를 defaults로 남기는 결과 화면(기존 지갑에서 연 등록, 복구 단어 없이 연결, 공장 관리자 PIN으로 한 슬롯 구성 바꾸기)에 "PIN을 설정하기 전에는 이 YubiKey로 서명하지 않습니다."와 `PIN 설정하기`, 그대로 `완료`를 누르면 한 번 묻는다(`Confirm::YkPinLater`: "…나중에 설정 → YubiKey에서 바꿀 수 있습니다.", [지금 PIN 설정] [나중에]). 설정의 YubiKey 카드 머리에 "PIN: 공장 기본값 — 서명 안 됨"과 주 버튼 `PIN 설정`. 막는 범위(카드 단위)는 그대로. 시험 `a_factory_pin_card_is_stopped_at_the_form_and_before_the_window`(띠와 `PIN 설정`, `검토` 꺼짐, 4100과 알림 한 번, defaults에서 빠지면 둘 다 풀림). spec/10 §9.3, spec/05 §4.9.
- **3-10 지우기 확인의 "지워지는 계정"**: 전 — EVM 가져온 키 삭제만 잔액 블록이 있었고, YubiKey 기록 지우기는 한 문단, 키 지우기·슬롯 바꾸기는 주소만, 복구 단어 지우기와 Solana·Bitcoin·Zcash 가져온 키 삭제는 계정 정보가 거의 없었다. 후 — 새 `ui::removed`(공용 블록): 계정마다 라벨·체인·§3.3 묶음 전체 주소·그 체인의 지금 네트워크 캐시에서 마지막으로 읽은 기본 자산 잔액(숨긴 계정 표시와 같은 캐시, 새 RPC 없음). 잔액이 0보다 크면 고위험 띠 "이 계정에 잔액이 있습니다: {값} ({네트워크}). 지우기 전에 다른 계정으로 옮기세요.", 모르면 주의 띠 "잔액을 확인하지 못했습니다(이 네트워크를 연 적 없음).", 0이면 흐린 줄. 영구히 잃는 키(경로를 모르고 다른 카드에 없는 카드 키, 가져온 키)는 그 문장을 T-YK-KEY-LOST나 가져온 키 삭제 띠(이제 고위험 띠) 안에 넣고, 다른 카드에 남는 키는 잔액을 흐린 줄로만 보인다. 쓰는 곳 여섯: ① YubiKey 기록 지우기 오버레이(한 문단을 블록과 계정별 "YubiKey #m(으)로 계속 서명"/"이 지갑에서 서명 불가 — …돌아옵니다" 줄로 나누고, "잃어버린 YubiKey라면: 기록을 지워도 카드의 키는 그대로입니다 — 백업 YubiKey나 복구 단어로 새 카드를 등록해 자산을 옮기세요.") ② YubiKey의 키 지우기 ③ 슬롯 구성 바꾸기 2단계의 빠지는 계정 ④ 설정 → 복구 단어 → 지우기(그 복구 단어의 EVM·Solana·Bitcoin·Zcash 계정) ⑤ EVM 가져온 키 삭제(이전 블록 대체) ⑥ Solana·Bitcoin·Zcash 가져온 키 삭제. 확인 오버레이·입력 단어·2초 누르기·흐름은 그대로. 시험 `ui::removed::tests::removed_accounts_say_their_last_balance`(순수 블록 함수). spec/04 §2.18.
- **3-11 PIN 잠김 문구를 키에 맞게**: 전 — OpenPGP PIN 잠김은 늘 "…OpenPGP 애플릿 초기화 뒤 다시 등록하세요"(복구 단어 없는 키는 초기화하면 영구히 사라짐), 관리자 PIN 잠김은 "…초기화 뒤 다시 등록해야 합니다"로 서명이 안 되는 것처럼 말했다. 후 — `yubikey::PinContext::of(records, serial, kind)`(그 애플릿 키를 모두 복구 단어로 다시 만들 수 있는지, 같은 키를 가진 백업 카드)와 `PinKind::error_text_in`·`CardJobError::text_for_in`을 더해 W11, W12, 설정 → YubiKey 작업 결과(통일·PIN 바꾸기·관리 키 보호·슬롯 바꾸기·지우기)에서 쓴다. 관리자 PIN 잠김 "…서명은 지금처럼 OpenPGP PIN으로 됩니다. 키 넣기·슬롯 구성 바꾸기·PIN 풀기만 막히며, 다시 쓰려면 OpenPGP 초기화(그 애플릿의 키가 지워짐)가 필요합니다."(맥락 없는 문장도 이것으로). OpenPGP PIN 잠김 — 복구 단어 있음 "…관리자 PIN으로 풀 수 있습니다(ykman openpgp access unblock-pin). 관리자 PIN도 모르면 OpenPGP 초기화 뒤 같은 복구 단어로 다시 등록하세요.", 복구 단어 없고 이 카드에만 "…이 키는 복구 단어가 없어 초기화하면 영구히 사라집니다. 관리자 PIN으로 PIN을 푸는 방법(…)만 쓰고 초기화하지 마세요.", 백업 카드가 있으면 "백업 YubiKey #{m}(으)로 계속 서명할 수 있습니다." PIV도 같은 꼴(PUK로 풀기, PUK도 잠기면 PIV 초기화 = Solana 키 삭제). 맥락을 모르면 이전 문장. 시험 `yubikey::tests::a_blocked_pin_of_a_key_without_words_never_advises_a_reset`. spec/10 §9.1.
- **3-12 YubiKey의 키 지우기 문구**: 전 — 라디오 "이 지갑의 슬롯만 지우기"/"애플릿 초기화 (PIN도 공장 기본값)"의 설명이 delete_key·RSA·TERMINATE/ACTIVATE로 시작했고, 제목은 "키 지우기"인데 버튼과 입력 단어는 "비우기"였다. 후 — 라디오 `이 지갑의 키만 지우기 (권장)` / `OpenPGP 전체 초기화 — 다른 키도 지움`, PIV `Solana 키만 지우기 (권장)` / `PIV 전체 초기화 — 인증서 등 다른 키도 지움`. 설명은 결과 먼저("이 지갑이 넣은 키만 지웁니다. 같은 YubiKey의 GPG 키·PIN·FIDO2(패스키)는 그대로입니다. 관리자 PIN이 필요합니다." / "OpenPGP 기능 전체를 공장 상태로 되돌립니다… PIN은 123456, 관리자 PIN은 12345678이 됩니다. PIN 없이 되며 되돌릴 수 없습니다.", PIV는 PIN 123456·PUK 12345678). 방법 설명은 "어떻게 지우나요 ▸" 안(이번 실행 메모리), 되돌릴 수 없다는 고위험 띠는 초기화 라디오 바로 아래. `CLEAR_WORD` "비우기" → "지우기", 실행 버튼 "이 YubiKey의 키 지우기", 카드 "무엇을 지울까요?". 입력 단어 확인 자체, LOSS_WORD·T-YK-KEY-LOST, 관리자 PIN 요구, APDU 순서는 그대로. spec/10 §15.2.
- **3-13 PIN 설정 카드 위치와 통일 기본값**: 전 — S21 결과 화면에서 PIN 카드는 슬롯·주소 카드 아래에 있었고, T-YK-PINS-FIRST는 버튼 바로 위, 기본값 띠는 항목마다 한 줄, PIN 안내 5줄이 버튼 앞이었으며 방식은 늘 "통일"로 시작했다. 후 — PIN 카드를 완료 띠 바로 아래로 올리고 슬롯·경로·주소는 "슬롯·주소 자세히 ▸"로 접는다(이번 실행 메모리). T-YK-PINS-FIRST는 PIN 카드 첫 줄. 기본값 띠는 한 줄 "공장 기본값: OpenPGP 관리자 PIN · PIV PIN · PIV 관리 키 — 아래 “PIN 설정하기” 한 번으로 모두 바꿉니다."(본 `DefaultsSeen` 항목만). 주 버튼을 먼저 두고 PIN 안내 5줄·잠김 설명·순서 설명은 "PIN 안내 ▸" 안. 설정 → YubiKey의 PIN 카드도 같은 배치. 방식 기본값은 이번 실행에 본 `DefaultsSeen`(등록·연결·슬롯 바꾸기)로: 셋 다 공장값이면 "통일", 일부만이면 "하나씩 따로"이고 바꿔야 할 버튼에 "(공장값 — 바꿔야 함)", 모르면 "통일"(사용자가 고르면 그 실행 동안 그대로, `CardUi::pins_chosen`). 통일 W12에 "지금 네 값이 모두 같을 때만(공장값이거나 전에 통일한 값) 쓰세요. 다르면 “하나씩 따로”를 쓰세요. 틀린 현재 값은 그 PIN의 남은 시도를 1회 줄입니다." `set_pins`의 순서·동작, 공장 PIN 거부, PIN 규칙, 새 지갑의 PIN 먼저 규칙은 그대로. 새 시험 없음. spec/10 §9.3.

### 3. 남긴 것과 이유·대안

- **D1 다중 모니터 실기 확인**(3-2): 이 PC(모니터 4대, AppliedDPI 144)에서 1080p·세로 모니터로 주 창을 옮겨 승인 창을 여는 실기 확인은 하지 않았다. 수동 체크리스트 UI-M3-14에 한 줄로 남겼다(배치 2 D7과 함께).
- **D2 길게 누르기 진행 "{0.0}초"**(3-3): 상태 줄은 "남은 시간 · 대기 · 상태 문구"만 두라고 했지만 길게 누르는 동안의 진행 초는 상호작용 피드백이라 상태 줄 끝에 남겼다(spec/04 §3.4의 표시).
- **D3 Permit2 `approve` 거래의 문장**(3-4): PermitSingle과 같은 문장을 쓰되 거래이므로 끝을 "…쓸 수 있게 하는 거래입니다."로 했다. 시뮬레이션 로그로 ERC-20/721이 정해지지 않은 `approve`(`amount_or_token_id`, R4)와 `decreaseAllowance`·ERC-721 개별 승인은 이전 문장이다. increaseAllowance의 금액은 늘리는 양(`added`)이다.
- **D4 구역 순서 시험**(3-5): 구역 순서를 단언하던 기존 시험은 없었다(고칠 것이 없음). 새 시험이 "핵심 정보"만 남는 순서를 단언한다. 합친 "참고:" 줄에서 여러 줄 경고 문구는 " — "로 이었다.
- **D5 이름의 두 꼴**(3-6): S10·S11·S12·활동은 배치 2의 "계정 1  [복구 단어 2]"(대괄호)를 그대로 쓰고, 사이트·세션·승인 창(`own_accounts`, Solana dApp 행)만 "계정 1 (복구 단어 2)"로 했다. Bitcoin dApp 행 이름은 BTC meta에 이름이 없어(배치 2 D3) 바꾸지 않았다. 비슷한 주소 사이트 경고·S13 카드 묶기·계정 바꾸기는 항목대로 하지 않았다.
- **D6 다른 카드의 일련번호**(3-8): "연결된 YubiKey(#{m})"는 꽂힌 카드가 하나일 때만 안다(작업자가 `single_card`로 읽기만). 둘 이상이면 "#m" 없이 "연결된 YubiKey에는 이 키가 없습니다 — #n을(를) 연결하세요"(조사는 번호의 끝소리에 맞춤, `ui::theme::object_particle`). Bitcoin 수수료 올리기 폼도 같은 자리에 안내를 둔다.
- **D7 4100의 이유**(3-9): 새 `ProviderError` 변형을 만들지 않고 4100 `Unauthorized`로 거절했다(확장·문서의 오류 표를 바꾸지 않기 위해; 이유는 앱의 알림이 말한다). Bitcoin 수수료 올리기 폼은 보내기 폼이 아니라 막지 않았다(카드 단계가 그대로 거부).
- **D8 잔액 캐시의 범위**(3-10): Bitcoin은 그 계정이 지금 네트워크에서 새로 고친 적이 있을 때만, Zcash는 그 네트워크의 마지막 새로 고침이 그 주소일 때만 알고, 나머지는 "확인하지 못했습니다" 주의 띠다. 토큰 잔액과 다른 네트워크는 보지 않는다 — 그래서 EVM 가져온 키 확인에만 있던 "다른 네트워크와 토큰 잔액은 여기서 확인하지 않았습니다" 줄을 블록의 마지막 줄(T-BALANCE-SCOPE "위 잔액은 지금 네트워크의 기본 자산만 마지막으로 읽은 값입니다 — 다른 네트워크와 토큰 잔액은 확인하지 않았습니다.")로 옮겨 여섯 곳 모두에 둔다(빠지는 계정이 있을 때).
- **D9 맥락을 모르는 잠김 문구**(3-11): 복구 단어 없이 연결하는 흐름(카드가 아직 기록에 없음)의 PIN 확인은 이전 문장을 쓴다. 관리자 PIN 잠김은 복구 단어 없는 키만 있는 카드면 "초기화하지 마세요"를 더했다.
- **D10 PIV 메타데이터 읽기·PIV 단계 건너뛰기**(3-13): 항목에서 뺀 대로 하지 않았다. 방식 기본값의 "셋"은 `DefaultsSeen`의 관리자 PIN·PIV PIN·PIV 관리 키다.
- **D11 화면 투어**: 바뀐 장면만 다시 찍었다(아래). YubiKey 기록 지우기·키 지우기·복구 단어 지우기·가져온 키 삭제의 확인 화면과 공장 PIN 띠는 투어에 장면이 없어 찍지 않았다.
