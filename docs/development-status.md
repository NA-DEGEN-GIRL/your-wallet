# 개발 현황과 제품 완성 기준

기준일: 2026-09-05. 정식 지갑은 아직 **STOP-SHIP**이다. Sepolia 실행판,
로컬 단위 테스트, 디버그 시험 경로의 성공을 정식 지갑 완성과 혼동하지 않는다.
`COMPILED_PARENT_POLICY`와 `COMPILED_RELEASE_POLICY`는 계속 `None`이다.

## 이번 구현: Phase 3D 승인 통신 시험

디버그 서비스의 Approval 프로브가 실제 네이티브 승인 화면을 호출하도록 연결했다.
화면 제목은 `Service transport test — no signing`이며, 서비스가 만든 요청에는
지갑 계정·네트워크·서명이 없다는 설명을 표시한다. 승인과 거부 모두 통신 시험
결과일 뿐이다. 결정값을 승인 정책이나 서명 권한으로 변환하지 않는다.

요청의 digest와 nonce는 매 실행 OS 난수로 새로 생성하는 공개 상관값이다.
뉴모닉·프라이빗키·예제 지갑은 생성하거나 사용하지 않는다.

통신 순서는 다음과 같다.

1. 기존 인증된 부트스트랩과 `HelperReady` 이후 72바이트 확인을 받는다.
   Approval은 이 시점에 응답 파이프를 닫지 않는다.
2. 서비스가 `YWKSAP01` 8바이트와 big-endian 길이 4바이트를 보낸 뒤,
   1~32,768바이트의 canonical Approval 요청을 보낸다.
3. UI는 요청을 한 번만 표시하고, 해당 digest·nonce에 묶인 75바이트 응답을
   보낸 뒤 응답 파이프를 닫는다. 요청 파이프는 계속 유지한다.
4. 서비스가 정확한 응답과 EOF를 확인하고, 등록된 동일 도우미의 실행 상태와
   역할을 새로 확인한 다음 프로세스/Job을 종료·회수한다.
5. 정리 후에도 처음의 절대 기한을 다시 검사해야 성공을 반환한다.
   실패나 기한 초과도 정리를 생략하지 않는다.

Secret Input은 여전히 확인 프레임 후 닫고 대기하는 ready-only 프로브다.
기존 5초 제한은 늘리지 않았다. 화면 자체의 상대 시간 표시는 서비스의 남은
절대 기한보다 길 수 있으므로 시험 화면은 더 일찍 종료될 수 있다.
이는 일반 사용자의 승인 입력 시간을 설계하거나 입증한 단계가 아니다.

검증 범위는 양쪽 코드의 단위·오류 주입 테스트와 실제 Windows 파이프의
단계별 입출력이다. 자동 테스트는 화면 클릭을 가장하거나 네이티브 창을 띄우지
않는다. 설치된 제한 서비스가 다른 세션의 실제 서명된 UI를 실행하고 사용자의
응답까지 완료했다는 E2E 증거는 아직 없다. Phase 3은 시작했지만 통과하지 않았다.
expected-peer 테스트는 기존 Phase 3A의 37개에 종료 직전 생존 검증 4개를 더한
총 41개이며, 과거 단계의 기록은 당시 기준으로 보존한다.

## 독립 데스크톱 클라이언트와 설치 시험 하네스

`key-agent-service-probe` 실행 파일과 플랫폼 내부 V2 클라이언트를 구현했다.
서비스 실행 기능과 독립된 명시적 디버그 feature에서만 활성화된다. 기존
Medium/interactive/비상승 토큰 정책, 정확한 현재 프로세스의 새 토큰 관찰,
스레드 토큰 부재를 각 호출 전에 확인한다. 새 공개 request ID로 같은 고정
packet-private 바인딩에서 `OpenEpoch` 직후 `LaunchApprovalRpcProbe`를 한 번만
보낸다. 중간 `Status`나 재시도는 없다. 처음의 5초 opening/25초 전체 기한을
유지하고, 응답의 canonical 형식·상관값·정확한 완료 종류를 확인한다.

기본/릴리스 실행은 통신 전에 조용히 78로 종료한다. 디버그 실행도 인자를
허용하지 않으며, 원시 프레임·식별값·경로·결정값은 출력하지 않는다. 성공 표시는
`SERVICE_APPROVAL_TRANSPORT_COMPLETED_NOT_RELEASE_EVIDENCE`다. 고정 endpoint와
packet privacy는 정확한 설치 서비스 이미지의 상호 신원 증거가 아니다.
local RPC에서는 OS의 call-timeout 옵션이 무시되므로 이 옵션에 의존하지 않는다.
별도 실행 파일의 25초 watchdog이 RPC와 출력/flush를 포함한 프로세스 수명을
제한하며, 만료 시 이 비서명 시험 프로세스만 78로 종료한다. 라이브러리 호출
자체가 중단된 RPC를 취소하거나 호출자 프로세스를 종료하는 것은 아니다.
실제 서비스의 정리 완료나 지원 Windows 전체의 동작은 별도 검증 대상이다.

[서비스 시험 하네스](../scripts/service-probe/README.md)는 비상승 빌드·준비와
관리자 설치/설정 읽기/시작/정지/제거를 분리한다. 네 개의 정확한 Cargo 산출물과
canonical 해시 manifest를 새 후보 폴더에 만들며 기존 후보는 덮어쓰지 않는다.
설치는 기존 서비스·설치 폴더를 채택하지 않고, 보호된 새 디렉터리·파일과 고정
가상 계정의 restricted service SID 설정을 사용한다. 서비스 권한은 정해진
네 privilege와 로그온 권한 중 누락된 것만 journal에 기록한 후 부여한다.
제거도 소유권·설정·파일·권한을 재확인한 정확한 대상에 한정한다. 불확실한
부분 상태는 자동 삭제하거나 복구하지 않고 보존한다.

이 하네스는 검토한 로컬 코드와 unsigned 디버그 산출물을 운영자가 신뢰하는
시험 도구다. 정식 설치물이나 서명된 바이너리의 증거가 아니다. 자동 검사는
준비·입력 검증·오류 주입과 네이티브 어댑터의 제한된 self-check이며, 실제
서비스를 설치하거나 LSA 권한을 바꾸거나 승인 창을 띄우지 않는다.

현재 호스트의 읽기 전용 확인에서는 `YourWalletKeyAgent`가 설치되어 있지
않았고 실행 토큰도 비상승 상태였다. 파일 접근 권한과 관리자 토큰은 별개다.
도구가 없던 이전 체크포인트와 달리 실행 절차는 구현했지만, 실제 제한 서비스의
설치·사용자 세션 도우미 왕복은 여전히 운영자 실행과 검증이 필요하다.
기존 current-user 검사나 현재 프로세스 V1 RPC 테스트가 이를 대신하지 않는다.
실제 비상승 준비 실행과 네 후보 파일의 단일 링크·크기·해시 재검증은 통과했다.
미설치 상태의 후보 클라이언트는 고정 unavailable 메시지와 78을 반환했고,
운영 하네스는 관리자 토큰이 필요하다는 20을 반환했다. 이는 정상 왕복이나
설치 성공의 증거가 아니라 현재의 실행 경계와 실패 시 차단을 확인한 결과다.

## 다음 구현 순서

1. 실제 서비스→사용자 세션의 비밀 없는 도우미 왕복을 검증하고,
   잠금·로그오프·사용자 전환의 SCM 이벤트를 기존 세션 취소 정책에 연결한다.
2. Broker 요청과 서비스의 승인 정책을 연결한다. Secret Input의 실제 입력
   통신·비밀 전달·폐기를 서비스 소유 상태와 결합한다.
3. 서비스 SID 아래 TPM 키 보관, rollback 방지, 내구성 저널 및 복구를 연결한다.
4. 승인한 표시 내용→서명→브로드캐스트와 장애 후 재서명 금지를 통합 검증한다.
5. 정확한 설치물·서명된 바이너리·지원 Windows/TPM 환경에서 공격 및 복구
   매트릭스와 독립 검토를 완료한 뒤에만 제한된 출시를 검토한다.

완성 기준은 [서비스 설계의 단계별 exit gate](designs/windows-key-agent-service.md)와
[출시 보안 요건](release-security.md)이다. 코드가 컴파일되거나 테스트가 통과했다는
이유로 설치·하드웨어·외부 검토 증거를 대체하거나 검사를 완화하지 않는다.

## 개발 하네스 사용 원칙

[개발 검사 안내](development.md)의 focused runner로 변경한 경로를 빠르게 검사한
뒤, 저장소 전체 검사와 별도의 release-policy 검사를 모두 수행한다. 아키텍처
검사는 새로 도달 가능한 경로와 실패 조건을 함께 고정한다. 기존 검사를 삭제하거나
해시만 바꿔 통과시키지 않는다. 로컬 fixture와 출시 증거는 별도로 보고한다.
